# JSTQB テスト技法一覧

テスト設計を行うスキルが、技法を選び、手順どおりに適用するための参照資料。
JSTQB（ISTQB の日本版）のシラバスに載っているテスト技法を、技法ごとに「何に使うか・どう作るか・何を数えれば十分か」の形でまとめる。

- 用語は JSTQB 日本語版シラバスの訳語に合わせ、括弧内に英語名を付ける
- 各技法の「例」は本資料のために作ったもので、シラバスの例ではない
- 調査日: 2026-11-13

## 0. 出典とシラバスの範囲

| シラバス | 版 | 本資料で扱う範囲 |
| --- | --- | --- |
| Foundation Level（FL） | V4.0（JSTQB 日本語版 V4.0.J02） | 第4章「テスト分析と設計」の全技法 |
| Advanced Level テストアナリスト（AL-TA） | v4.0（2025年、日本語版 V4.0.J01） | 第3章「テスト技法」の全技法と技法の選び方 |
| Advanced Level テクニカルテストアナリスト（AL-TTA） | v4.0（2021年） | 第2章「ホワイトボックステスト技法」 |

性能・セキュリティ・使用性などの品質特性テストは「テストタイプ」であり技法ではないため、本資料では扱わない。

## 1. 技法の分類

FL と AL-TA で分類の切り口が違う。技法そのものは共通しているので、両方を対応づけて示す。

| FL の分類 | AL-TA の分類 | 技法 |
| --- | --- | --- |
| ブラックボックス（仕様ベース） | データに基づく技法 | 同値分割法、境界値分析、ドメインテスト、組み合わせテスト、ランダムテスト |
| 〃 | 振る舞いに基づく技法 | 状態遷移テスト、CRUDテスト、シナリオベースドテスト（ユースケーステスト） |
| 〃 | ルールに基づく技法 | デシジョンテーブルテスト、メタモルフィックテスト |
| ホワイトボックス（構造ベース） | （AL-TTA で扱う） | ステートメントテスト、ブランチテスト／デシジョンテスト、MC/DCテスト、複数条件テスト、APIテスト |
| 経験ベース | 経験ベースのテスト | エラー推測（フォールト攻撃）、探索的テスト（セッションベースドテスト）、チェックリストベースドテスト、クラウドテスト |
| コラボレーションベースのアプローチ | — | ユーザーストーリーの共同執筆、受け入れ基準、受け入れテスト駆動開発（ATDD） |

- **ブラックボックス技法**: 仕様上の振る舞いからテストを導く。内部構造を見ないので、実装が変わっても振る舞いが同じならテストは使い回せる
- **ホワイトボックス技法**: コードの構造からテストを導く。設計・実装ができてから作る。仕様にない欠落（未実装の要件）は見つけられない
- **経験ベース技法**: テスト担当者の知識と経験を使う。他の技法で漏れる欠陥を拾う補完の位置づけ。効果は担当者のスキルに強く依存する
- **コラボレーションベースのアプローチ**: 欠陥を「見つける」より、意思疎通のずれによる欠陥を「作らない」ことに重心がある

### 共通の用語

| 用語 | 意味 |
| --- | --- |
| テスト条件 | テストで確認すべき事柄（何をテストするか） |
| カバレッジアイテム | 技法が「これを全部通せ」と定める単位（パーティション、境界値、遷移、ルール、分岐など） |
| カバレッジ | 通したカバレッジアイテム数 ÷ 識別したカバレッジアイテム総数（%） |
| 包含（subsume） | 基準Aを100%満たすテスト集合が必ず基準Bも100%満たすとき、AはBを包含する |

## 2. ブラックボックステスト技法（データに基づく技法）

### 2.1 同値分割法（Equivalence Partitioning, EP）［FL］

**考え方**: 同じように処理されるはずの値をひとまとまり（同値パーティション）にし、各パーティションから代表値を1つ選べば十分とみなす。

**適用場面**: 入力・出力・設定値・内部値・時間に関する値・インターフェースのパラメーターなど、値の範囲や種類で処理が分かれるもの全般。

**手順**
1. テスト対象のデータ要素（入力項目など）を洗い出す
2. 要素ごとに、処理が同じになる値の集合へ分割する。パーティションは互いに重ならず、空であってはならない
3. 各パーティションを「有効」（処理すべき値）と「無効」（拒否・無視すべき値）に分類する
4. 各パーティションから代表値を1つ選んでテストケースにする

**カバレッジ**: カバレッジアイテム＝パーティション。無効パーティションを含め、全パーティションを1回以上通す。
- 無効パーティションは、1つのテストケースに1つだけ入れる（複数入れると、どれで弾かれたか分からなくなる＝欠陥のマスキング）
- 複数の入力項目があるときの最低ラインは **イーチチョイスカバレッジ**（各項目の各パーティションを最低1回ずつ通す。組み合わせは問わない）

**例**: 会員登録の年齢欄。18〜65歳の整数のみ登録可。

| パーティション | 種類 | 代表値 |
| --- | --- | --- |
| 17以下 | 無効 | 10 |
| 18〜65 | 有効 | 30 |
| 66以上 | 無効 | 80 |
| 数値以外 | 無効 | "abc" |

→ 4テストケースで100%。

**検出できる欠陥**: パーティションの処理そのものの誤り（有効値を拒否する、無効値を受け付ける）。

### 2.2 境界値分析（Boundary Value Analysis, BVA）［FL］

**考え方**: 開発者は境界でミスしやすい（`<` と `<=` の取り違え、境界のずれ、境界の欠落）。パーティションの端に集中してテストする。

**適用場面**: 順序のあるパーティション（数値、日付、文字数など）にのみ使える。

**手順**
1. 同値分割法でパーティションを作る
2. 各パーティションの最小値・最大値（境界値）を特定する
3. 下記の 2値BVA か 3値BVA でカバレッジアイテムを決める

**カバレッジ**
- **2値BVA**: 境界値ごとに「境界値」と「隣のパーティションにある最も近い値」の2つ
- **3値BVA**: 境界値ごとに「境界値」と「その両隣の値」の3つ。2値より厳密

**例**: 2.1 の年齢欄（境界値は 17 / 18 / 65 / 66）

| 方式 | テストする値 |
| --- | --- |
| 2値BVA | 17, 18, 65, 66 |
| 3値BVA | 16, 17, 18, 19, 64, 65, 66, 67 |

3値が必要になる例: 仕様 `if (x <= 10)` を誤って `if (x == 10)` と実装した場合、2値BVA の x=10, 11 では結果が仕様と一致して見逃すが、3値BVA の x=9 で検出できる。

### 2.3 ドメインテスト（Domain Testing）［AL-TA］

**考え方**: 同値分割法と境界値分析を、**複数の変数が絡む条件**で定義されたパーティションへ拡張したもの。パーティションの境界は「原子条件」（`x + y <= 10` など）ごとに1本ずつある。

**適用場面**: 複数の変数の組み合わせで処理が変わる数値計算・判定（例: 身長と体重から判定する、金額と日数から料率が決まる）。全テストレベルで使える。

**境界の種類**
- 閉じた境界: `<=`, `>=`, `=` で作られる（境界上の点がパーティションに含まれる）
- 開いた境界: `<`, `>`, `≠` で作られる（境界上の点がパーティションに含まれない）

**カバレッジアイテム（点の種類）**

| 点 | 閉じた境界の場合 | 開いた境界の場合 |
| --- | --- | --- |
| ON | 境界上の点 | パーティション内で境界に最も近い点 |
| OFF | パーティション外で境界に最も近い点 | 境界上の点 |
| IN | パーティション内で、ON でない点 | 同左 |
| OUT | パーティション外で、OFF でない点 | 同左 |

**カバレッジ基準**

| 基準 | `<` `<=` `>` `>=` の境界ごと | `=` の境界 | `≠` の境界 |
| --- | --- | --- | --- |
| 簡易ドメインカバレッジ | ON 1つ、OFF 1つ | ON 1つ、両側の OFF 2つ | OFF 1つ、両側の ON 2つ |
| 信頼性の高いドメインカバレッジ | ON・OFF・IN・OUT を各1つ | 同上 | 同上 |

- OFF は対応する ON に、精度の範囲で可能な限り近づける
- 点は複数の境界で使い回せる（共通の IN 点、隣接パーティションの ON/OFF の流用）
- 信頼性の高いドメインカバレッジは点が少し増えるが、検出できるドメイン欠陥がかなり多い

**例**: 整数 x, y について「`x + y <= 10` かつ `x >= 0`」で受け付ける（精度1）。

| 境界 | ON | OFF | IN | OUT |
| --- | --- | --- | --- | --- |
| `x + y <= 10`（閉） | (3, 7) | (3, 8) | (2, 2) | (8, 8) |
| `x >= 0`（閉） | (0, 5) | (-1, 5) | (2, 2) | (-5, 3) |

**検出できる欠陥**: 演算子の誤り、定数の誤り、境界の傾き・位置の誤りなど、パーティションの実装ミス。

### 2.4 組み合わせテスト（Combinatorial Testing）［AL-TA］

**考え方**: 故障の多くは、1つのパラメーター値か、少数のパラメーターの組み合わせで起きる（ある調査では約97%が1〜2個の条件の相互作用によるもの）。全組み合わせではなく、組み合わせの一部を体系的に網羅する。

**適用場面**
- 構成パラメーター（OS、ブラウザ、言語設定など）の組み合わせ。同じテストケースを各構成で流す
- 入力データの組み合わせ。組み合わせごとに完全なテストケースを作る

**手順**
1. パラメーターと値を洗い出す。値が多いときは先に同値分割法で絞る（クラシフィケーションツリーやフィーチャーモデルで整理するとよい）
2. カバレッジ基準を選ぶ
3. 組み合わせを生成する（ペアワイズはツールを使うのが普通。PICT など）
4. 制約（ありえない組み合わせ）を除き、問題が既知の組み合わせを手で足す

**カバレッジ基準**
- **ベースチョイスカバレッジ**: パラメーターごとに基準値（最も重要な値）を決め、全基準値の組をベースにする。そこから1パラメーターずつ、基準値以外の値に差し替えた組を作る
- **ペアワイズカバレッジ**: 任意の2パラメーターの値の組をすべて1回以上含める
- より強い基準として n-wise（3パラメーター以上の組を網羅）などがある。リスクが高いほど強い基準を選ぶ

**例**: OS {Win, Mac}、ブラウザ {Chrome, Edge, Firefox}、言語 {ja, en}。全組み合わせは 2×3×2＝12 通り。

ペアワイズ（6通り）:

| # | OS | ブラウザ | 言語 |
| --- | --- | --- | --- |
| 1 | Win | Chrome | ja |
| 2 | Mac | Chrome | en |
| 3 | Win | Edge | en |
| 4 | Mac | Edge | ja |
| 5 | Win | Firefox | ja |
| 6 | Mac | Firefox | en |

ベースチョイス（基準 Win / Chrome / ja、5通り）: (Win, Chrome, ja), (Mac, Chrome, ja), (Win, Edge, ja), (Win, Firefox, ja), (Win, Chrome, en)

---

### 2.5 ランダムテスト（Random Testing）［AL-TA］

**考え方**: 入力ドメインから、決めた確率分布に従って入力をランダムに選ぶ。

**分布の選び方**
- 妥当性確認（validation）が目的: 運用プロファイル（実際の使われ方）に基づく分布
- 検証（verification）が目的: 偏りを避けるため、使われ方に依存しない分布

**種類**
- ガイドなし: 分布を最後まで固定する
- ガイドあり: それまでに選んだ値に応じて分布を変える（例: 適応ランダムテスト。欠陥が特定の領域に固まりやすい性質を利用し、ドメインを満遍なく覆う）

**カバレッジ**: 認められたカバレッジ基準はない。終了基準は実行件数や時間で決める。

**向いている場面**: ドメイン知識が少ない、大量のテストデータが必要、テスト担当者の思い込みによる見落としを避けたい。ファズテストやカオスエンジニアリングにも使われる。

**注意点**: 期待結果を自動で判定するテストオラクルがほぼ必須。データの意味を考えないため意味に関わる欠陥を見逃す、冗長なテストが出る、結果の再現性が下がる。

## 3. ブラックボックステスト技法（振る舞いに基づく技法）

### 3.1 状態遷移テスト（State Transition Testing）［FL / AL-TA］

**考え方**: 同じイベントでも、現在の状態によって反応が変わるシステムを、状態と遷移のモデルで表してテストする。

**適用場面**: 組込み・制御システム、画面遷移・対話型システム、ワークフロー、エンティティのライフサイクル（注文、申請など）。全テストレベルで使える。

**モデルの表し方**
- **状態遷移図**: ノード＝状態、矢印＝遷移。遷移のラベルは「イベント [ガード条件] / アクション」
- **状態表**: 行＝状態、列＝イベント（とガード条件）、セル＝遷移先とアクション。**無効な遷移を空セルとして明示できる**のが図との違い

**手順**
1. 状態、イベント、ガード条件、アクションを特定し、状態遷移図または状態表を作る（テストベースにモデルがあれば、テストに必要な粒度かを確認し、足りなければ作り直す）
2. カバレッジ基準を選ぶ
3. 基準を満たすイベントの並びをテストケースにする。1つのテストケースで複数の遷移を通してよい

**カバレッジ基準**（下ほど強い）

| 基準 | カバレッジアイテム | 出典 |
| --- | --- | --- |
| 全状態カバレッジ | 状態 | FL |
| 有効遷移カバレッジ（0スイッチカバレッジ） | 有効な遷移1つ。**最もよく使われる** | FL |
| 全遷移カバレッジ | 状態表の全遷移（有効な遷移を通し、無効な遷移を試みる）。ミッションクリティカル・セーフティクリティカルでは最低要件とすべき | FL |
| Nスイッチカバレッジ | N+1個の連続した有効遷移の並び。1スイッチ＝ある状態への入る遷移と出る遷移の組。実務では0・1スイッチが多い。2スイッチ以上は数が指数的に増えるため、想定外のイベント順による故障リスクが高いときだけ | AL-TA |
| ラウンドトリップカバレッジ | 開始と終了が同じ状態で、途中に同じ状態が2回現れないループ。欠陥検出に効果が高いと報告されている | AL-TA |

- 有効遷移を100%通せば全状態も100%になる。全遷移を100%通せば有効遷移と全状態も100%になる
- 無効な遷移は1テストケースに1つだけ入れる（マスキングを避ける）

**例**: ログインのロック機能（3回続けてパスワードを誤るとロック）

遷移:

| ID | 遷移元 | イベント [ガード] / アクション | 遷移先 |
| --- | --- | --- | --- |
| T1 | 未ログイン | 正しいPW / 失敗回数リセット | ログイン済 |
| T2 | 未ログイン | 誤ったPW [失敗回数 < 2] / 失敗回数+1 | 未ログイン |
| T3 | 未ログイン | 誤ったPW [失敗回数 = 2] / ロック通知 | ロック |
| T4 | ログイン済 | ログアウト | 未ログイン |
| T5 | ロック | 管理者が解除 / 失敗回数リセット | 未ログイン |

状態表（空欄＝無効な遷移）:

| 状態 ＼ イベント | 正しいPW | 誤ったPW | ログアウト | 管理者が解除 |
| --- | --- | --- | --- | --- |
| 未ログイン | T1 → ログイン済 | T2 / T3 | | |
| ログイン済 | | | T4 → 未ログイン | |
| ロック | | | | T5 → 未ログイン |

- 有効遷移カバレッジ: 「T2 → T2 → T3 → T5 → T1 → T4」の1本で T1〜T5 をすべて通せる
- 全遷移カバレッジ: 上に加え、空欄8つ（例: ロック中に正しいPWを入れる）を、1テストケースに1つずつ試みる
- ラウンドトリップ: 「未ログイン→ログイン済→未ログイン」(T1, T4)、「未ログイン→ロック→未ログイン」(T3, T5)、「未ログイン→未ログイン」(T2)
- ガード条件の境界（失敗回数 1 / 2）には境界値分析を組み合わせる

**検出できる欠陥**: 誤った遷移先、欠けた遷移、ロック中の操作を受け付けるなど無効な遷移の誤受理、アクションの誤り。モデル化の過程で仕様の欠陥も見つかる。

### 3.2 CRUDテスト（CRUD Testing）［AL-TA］

**考え方**: データエンティティ（会員、注文など）のライフサイクル（作成 Create・読み込み Read・更新 Update・削除 Delete）が、機能の間で一貫して扱われているかを確認する。

**適用場面**: 主にシステムテスト。データを扱う業務システム。

**手順**
1. **CRUDマトリクス**を作る。列＝エンティティ、行＝機能、セル＝その機能がそのエンティティに行う操作（C/R/U/D）。C・U・D に暗黙的に伴う R を見落とさない
2. **完全性テスト**（静的）: 各エンティティに C・R・U・D がすべて揃っているかを確認する。欠けていれば調査が必要な異常
3. **一貫性テスト**（動的）: エンティティごとに、機能を組み合わせてライフサイクル全体をたどるテストケースを作る。マトリクスの全操作を通し、ネガティブテスト（未作成のエンティティを読む、削除済みを更新する等）も含める

**カバレッジ**: 実行した操作数 ÷ CRUDマトリクスの操作総数。より厳密には操作の組み合わせ（例: 各 U の後にすべての R）をアイテムにする。

**例**

| 機能 ＼ エンティティ | 会員 | 注文 |
| --- | --- | --- |
| 会員登録 | C | |
| 会員情報変更 | R U | |
| 退会 | R D | R |
| 注文作成 | R | C |
| 注文履歴閲覧 | R | R |
| 注文キャンセル | | R U |

完全性テストの指摘: 「注文」に D がない → 削除しない仕様なのか、実装漏れなのかを確認する。

**検出できる欠陥**: データ整合性の違反、アクセス制御の欠陥、機能間のデータ不整合（退会した会員の注文が残る等）。

---

### 3.3 シナリオベースドテスト（Scenario-Based Testing）［AL-TA］（FL 旧版の「ユースケーステスト」を含む）

**考え方**: 現実的な利用シナリオ（業務の流れ）をモデル化し、そのシナリオを通してテストする。

**適用場面**: システムテスト・受け入れテストのエンドツーエンドテストが中心。統合テスト（コンポーネント間のやり取り）や、非機能テストの運用プロファイル作りにも使える。

**モデル**
- **アクティビティ図**: 業務プロセスや制御フローを表す。開始・終了ノード、アクション、分岐・合流、並行処理（フォーク・ジョイン）、スイムレーン
- **ユースケース**: ユーザーとシステムのやり取りの記述。3種類のシナリオを区別する
  - メインシナリオ（ハッピーパス）: 目的を達成する典型的な流れ。1つのユースケースに1つだけ
  - 拡張（代替シナリオ）: 別の流れだが最終的に目的を達成する
  - 例外: 異常な操作や無効な入力で目的を達成できない流れ
- ほかにフローチャート、BPMN、シーケンス図など。シナリオの発見にはユーザーストーリー、ペルソナ、カスタマージャーニーマップが役立つ

**カバレッジ**
- 実行したシナリオ数 ÷ 識別したシナリオ総数
- ループがあるとパスが無限になるため **シンプルループカバレッジ** を使う: 各ループを 0回（スキップ）、1回、複数回（典型的な回数）、最大回数（可能なら）で実行
- シナリオ中の変数に同値分割法・境界値分析を重ねると、1シナリオに複数のテストケースが必要になる

**例**: 「商品を購入する」ユースケース
- メイン: 商品をカートに入れる → 購入手続き → カード決済 → 注文完了
- 拡張: 決済方法をコンビニ払いに変える → 注文完了
- 例外: カードの承認が通らない → 購入できずエラー表示
- ループ: カートへの追加を 0回（空のまま購入手続き）／1回／3回／上限回数

## 4. ブラックボックステスト技法（ルールに基づく技法）

### 4.1 デシジョンテーブルテスト（Decision Table Testing）［FL / AL-TA］

**考え方**: 条件の組み合わせで結果が変わるルール（業務ルールなど）を表に整理し、組み合わせの漏れなくテストする。状態によらないロジックが対象。

**適用場面**: 複雑な業務ルール、料金・割引・審査の判定、権限の判定。

**表の作り方**
- 行: 条件とアクション。列: ルール（条件値の一意な組み合わせと、それに対応するアクション）
- 条件の表記: T（真）、F（偽）、`-`（結果に無関係＝ドントケア）、N/A（そのルールでは実現不可能）
- アクションの表記: X（発生する）、空白（発生しない）
- 制限指定（すべて真偽値）と拡張指定（範囲・パーティション・離散値を取る）がある

**手順**
1. 条件とアクションを洗い出す
2. 全組み合わせの「完全なデシジョンテーブル」を作る（列数＝各条件の値の数の積）
3. 実現不可能な組み合わせの列を除く
4. 必要なら最小化する（下記）
5. 表をレビューする: **一貫性**（同じ条件値に2つのルールが当たるならアクションが等しい）、**実現可能性**、**完全性**（実現可能な組み合わせの欠落がない）、**正確性**（意図した振る舞いを表している）。加えてルール同士が重ならないことが望ましい
6. 各列をテストケースにする

**最小化（AL-TA）**: アクションが同じで、1つの条件だけが違い、その条件の全値を覆う列同士を `-` で統合する。統合の順序で結果が変わり、最適とは限らない。
- **チェックサム法**: 最小化後の各ルールについて、元の表の何列分にあたるかを数える（`-` 1つにつき、その条件の値の数を掛ける）。合計が元の表の列数より少なければ欠落、多ければ重複や不要なルールがある。一致しても等価の保証にはならない

**カバレッジ**: 通した列数 ÷ 実現可能な列の総数。**リスクが高い場合は最小化せず**、完全な表の実現可能な列で測る。`-` の列をテストするときは、どの具体値で実装するかを決める必要がある。

**例**: 送料無料の判定。ルール: 「会員で購入額5,000円以上」または「送料無料クーポンあり」なら送料無料。

完全なデシジョンテーブル（8列）:

| | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 会員 | T | T | T | T | F | F | F | F |
| 購入額 ≥ 5,000円 | T | T | F | F | T | T | F | F |
| クーポンあり | T | F | T | F | T | F | T | F |
| 送料無料 | X | X | X | | X | | X | |

最小化後（4列）:

| | M1 | M2 | M3 | M4 |
| --- | --- | --- | --- | --- |
| 会員 | - | T | T | F |
| 購入額 ≥ 5,000円 | - | T | F | - |
| クーポンあり | T | F | F | F |
| 送料無料 | X | X | | |
| チェックサム | 4 | 1 | 1 | 2 |

チェックサム 4＋1＋1＋2＝8 で、元の8列と一致する。

**検出できる欠陥**: 条件の組み合わせ漏れ、ロジックの誤り。要件の矛盾や抜けも見つかる。

---

### 4.2 メタモルフィックテスト（Metamorphic Testing, MT）［AL-TA］

**考え方**: 期待結果を個別に決められなくても、「入力をこう変えたら、出力はこう変わるはず」という関係（**メタモルフィック関係, MR**）なら書けることがある。元のテストケース（ソーステストケース）からMRに従って派生テストケース（フォローアップテストケース）を作り、両者の結果がMRを満たすかで合否を判定する。

**適用場面**
- **テストオラクル問題**がある（正しい出力が分からない）: AI、シミュレーション、検索、最適化、科学計算
- テスト設計と実行を自動化して大量に回したい（ランダムテストと組み合わせる）
- 非機能テスト（MRで負荷を作る、インストールパラメーターの順序を変える等）
- AIベースのシステムで推奨される技法

**手順**
1. テスト対象の性質からMRを見つける
2. ソーステストケースを作る（ランダム生成でもよい）
3. MRでフォローアップテストケースを作る（複数のMRを組み合わせてもよい）
4. ソースとフォローアップをまとめて1つのテスト手順にし、結果がMRを満たすかを判定する。不合格ならどちらのテストケースが悪いかをデバッグで切り分ける

**カバレッジ**: 認められた基準はない。各MRを1回通すだけでは不十分。

**例**
- 平均を求める関数: 入力の順序を入れ替えても平均は変わらない／全要素を x 倍すると平均も x 倍になる
- 商品検索: 検索条件を AND で1つ足すと、結果件数は増えない
- 寿命予測AI: 喫煙本数を増やすと、予測寿命は延びない

---

## 5. ホワイトボックステスト技法

FL はステートメントテストとブランチテストのみ。より厳密な技法は AL-TTA で扱う。

### 5.1 ステートメントテスト（Statement Testing）［FL / AL-TTA］

- **カバレッジアイテム**: 実行可能なステートメント（文）
- **カバレッジ**: 実行したステートメント数 ÷ 実行可能なステートメント総数
- **位置づけ**: テストするコードの最低ラインとして100%を目指すべき（到達不能コードがあると100%にできない）
- **限界**: 100%でも判定ロジックを全部試したことにはならない。データ依存の欠陥（分母が0のときだけ起きるゼロ除算など）も見逃しうる

### 5.2 ブランチテスト（Branch Testing）［FL］／デシジョンテスト（Decision Testing）［AL-TTA］

- **ブランチ**: 制御フローグラフのノード間の制御の移動。無条件（直列のコード）と条件付き（判定結果）がある
- **デシジョン**: if の真偽、case の各分岐、ループの継続・終了といった判定の結果
- **カバレッジ**: 通したブランチ数（判定結果数）÷ 総数
- 100%ではほぼ同じテスト集合になるため、ブランチテストとデシジョンテストは同義に使われることが多い（判定が1つもないコードの扱いだけが違う）
- **ブランチカバレッジはステートメントカバレッジを包含する**（逆は成り立たない）
- **限界**: 判定の中の複数の条件の組み合わせは見ない。特定のパスでしか起きない欠陥は見逃しうる
- コードだけでなく、判定を含むモデル（業務プロセスモデル）にも適用できる

### 5.3 MC/DCテスト（Modified Condition/Decision Testing）［AL-TTA］

- **考え方**: 判定が複数の原子条件からなるとき、**各原子条件が単独で判定結果を変えられること**を、条件1つだけを変えたテストの組で示す
- **テスト数**: 互いに独立な原子条件が N 個なら、通常 N+1 回の実行で達成できる
- **適用場面**: 航空・自動車などセーフティクリティカルなシステム。デシジョンテストより厳密で、複数条件テストよりテスト数がずっと少ない中間点
- **難しさ**: 同じ変数が判定内に複数回出て条件が「結合」していると、1条件だけを変えられないことがある。短絡評価（`A && B` で A が偽なら B を評価しない）で一部の組み合わせが実行できないことがある
- **例**: `if (A && B)` → (A, B) = (T, T)→真、(F, T)→偽、(T, F)→偽 の3件。1件目と2件目で A の、1件目と3件目で B の独立した影響を示せる

### 5.4 複数条件テスト（Multiple Condition Testing）［AL-TTA］

- **カバレッジアイテム**: 判定内の原子条件の真偽の全組み合わせ（N 個なら 2^N）
- **適用場面**: 高リスクのソフトウェア、長期間止まらずに動くべき組込みソフトウェア
- **限界**: テスト数が爆発するため、条件が多いときは MC/DC のほうが現実的。短絡評価で実行できる組み合わせが減ることがある
- **例**: `if (A && B)` → (T,T), (T,F), (F,T), (F,F) の4件

### 5.5 APIテスト（API Testing）［AL-TTA］

技法というよりテストタイプ。GUI テストに似ており、入力値と返却データの評価が中心。

- **重視すること**: ネガティブテスト（想定外の使い方への頑健なエラー処理）、多数のパラメーターの組み合わせテスト、疎結合によるトランザクション消失・タイミング不良に備えたリカバリー・リトライの確認、高い可用性
- **カバレッジ**: 決まった基準はない。最低限、現実的な入力と想定外の入力で呼ぶ。より厳密には全エンドポイント・全機能を1回以上呼ぶ。REST API では入力側（全操作、全パラメーター、操作の並び）と出力側（全ステータスコード、全プロパティを含むレスポンス）の基準がある
- **検出できる欠陥**: インターフェースの不整合、データ処理、タイミング、トランザクションの消失・重複、例外処理

### 5.6 包含関係と選び方［AL-TTA］

```
複数条件カバレッジ ⊇ MC/DC ⊇ デシジョン（≒ブランチ）カバレッジ ⊇ ステートメントカバレッジ
```

- ふつうはブラックボックス技法を先に適用し、コードカバレッジを測り、足りないところだけホワイトボックス技法でテストを足す
- 要求するカバレッジは **100%で指定する** のがよい。80%を許すと、未テストで残るのは最もテストしにくく、最も複雑で欠陥の多い部分になりがち（ISO 29119-4 では実現不可能なアイテムを分母から除けるので100%を目標にできる）
- 指定する基準は1つでよい（包含関係があるため）。システムの部位ごとにリスクに応じて変えてよい
- 安全関連システムでは規格が要求水準を決める。例: IEC 61508 では SIL 3 でブランチカバレッジ100%が強く推奨、SIL 4 で MC/DC 100%も強く推奨。ISO 26262（自動車）や DO-178C（航空）では別の水準
- 非安全関連システムでは、契約、顧客要求、業界規制、組織のテスト戦略、コーディングスタイル（複合条件がなければ MC/DC は無駄）、過去の欠陥データ、担当者のスキル、計測ツールの有無で決める

## 6. 経験ベースのテスト技法

### 6.1 エラー推測（Error Guessing）［FL］

**考え方**: テスト担当者の知識から、起きそうなエラー・欠陥・故障を予測してテストする。

**予測の材料**
- そのアプリケーションの過去の動き
- 開発者が起こしやすいエラーの種類と、それが生む欠陥の種類
- 似たアプリケーションで起きた故障の種類

**狙う欠陥の典型**: 入力（正しい入力を拒否する、パラメーターの誤り・不足）、出力（形式の誤り、結果の誤り）、ロジック（条件の欠落、演算子の誤り）、計算（オペランドの誤り）、インターフェース（パラメーターの不一致、型の非互換）、データ（初期化の誤り、型の誤り）

**フォールト攻撃（Fault Attack）**: エラー推測を体系的に行う方法。想定されるエラー・欠陥・故障のリストを作るか入手し、それぞれを露呈させるテストを設計する。リストは経験、欠陥・故障データ、ソフトウェアが失敗する理由の一般知識から作る。

---

### 6.2 探索的テスト（Exploratory Testing）［FL / AL-TA］

**考え方**: テスト対象について学びながら、テストの設計・実行・評価を同時に行う。

**適用場面**: 仕様が少ない・不十分、スケジュールが厳しい、形式的な技法を補完したい。経験とドメイン知識があり、分析力・好奇心・創造性の高い担当者ほど効果が高い。ドメイン知識がほぼない場合は効果が出にくい。他の技法（同値分割法など）と併用できる。

**セッションベースドテスト**（探索的テストを体系立てて行う方法）
1. **テストチャーター**を作る（下記）
2. 決めた時間枠（タイムボックス）の中でテストする
3. **テストセッションシート**に、実行した手順、発見した事象、疑問、次のテストのアイデアを記録する
4. セッション後に関係者と**デブリーフィング**（振り返りの議論）を行う

**テストチャーター**［AL-TA］
- 基本形式（ミッション）: 「**[対象] を [リソース] を使って探索し、[情報] を発見する**」（Explore [target] With [resources] To discover [information]）
  - 対象: 領域、機能、リスク、コンポーネント、要件
  - リソース: テストデータ、構成、ツール、制約、ヒューリスティック、依存関係
  - 情報: 品質特性の評価、想定する欠陥の種類、標準への違反
- 追加してよい情報: セッションの時間・日時・担当者、テスト目的、スコープ（対象領域、使う技法、テストアイデア、終了基準、優先度、テストしないこと）、開始基準、製品情報、制限事項（製品が絶対にしてはならないこと）、テスト環境、使えるデータやツール、過去の欠陥やオープンな疑問、規制や標準
- 設計時に考慮する要因: 顧客・要求（要件、業務ユースケース、品質要求、カスタマージャーニーマップ）、製品（機能フロー、主目的、設計、インターフェース）、プロジェクト管理（時間、目的、工数、ビジネス価値）
- 書き込みすぎると探索の自由が減る。逆に「製品がしないこと」を書くと誤検知の報告を減らせる

**例**: 「会員登録画面を、境界値と不正文字を含むテストデータを使って探索し、入力チェックの漏れとエラーメッセージの不備を発見する」（60分）

---

### 6.3 チェックリストベースドテスト（Checklist-Based Testing）［FL / AL-TA］

**考え方**: チェックリストの項目（テスト条件）を覆うようにテストを設計・実行する。チェックリストは過去の故障・欠陥の経験を記録したもの。

**チェックリストの種類**［AL-TA］
- **リード・ドゥ型**: 書かれたとおりに確認する具体的な項目（例: 入力欄に入れる具体的な不正値の一覧）
- **ドゥ・コンファーム型**: 考え方を導く観点の項目（例: 検索結果が利用者にとって妥当か）

**作り方**［AL-TA］
1. スコープ、目的、形式（上記2種）を決める
2. 項目の材料を集める: 経験者の知見、欠陥ライブラリーや欠陥分類、ドキュメント、リスク、既存テストケース
3. 項目を書く: はい／いいえ／該当なし で答えられる質問形式。明確・具体的・一貫・保守可能・実行可能・測定可能に。重要度・影響・リスクで優先度を付ける
4. 機能領域、ユーザーの役割、テストレベルなどで分類して整理する

**運用上の注意**［FL］
- 自動でチェックできる項目、開始・終了基準向きの項目、一般的すぎる項目は入れない
- 開発者が同じミスを避けるようになると効かなくなる項目がある。欠陥分析に基づいて定期的に更新する。ただし長くしすぎない
- 詳細なテストケースがない場合に一貫性を与える。ハイレベルな項目ほど実行にばらつきが出て、カバレッジは広がるが再現性は下がる
- 非機能にも使える（例: 使用性の10のヒューリスティック）

---

### 6.4 クラウドテスト（Crowd Testing）［AL-TA］

**考え方**: 背景や場所の異なる多数のテスト担当者（社内外）にテストを分散する。テスト技法を適用する担当者の代わりにはならないが、テスト環境の多様性を補う。

| メリット | 制約 |
| --- | --- |
| 多様な環境（地域、端末、ブラウザ、ネットワーク） | テストの質が担当者によってばらつく |
| 短時間で規模を拡大できる | 時差・文化・言語による意思疎通の難しさ |
| 社内で大規模チームを持つより安い | 外部へソフトウェアを渡すセキュリティ・機密のリスク |
| フィードバックが速い | 大量の報告（重複・誤検知を含む）の管理 |
| 実ユーザーの視点（使用性、受け入れテストで有効） | 再現性が低い（その分カバレッジは広がる） |

---

## 7. コラボレーションベースのテストアプローチ［FL］

### 7.1 ユーザーストーリーの共同執筆

- ユーザーストーリーは、利用者や購入者にとって価値のある機能を表す
- **3つのC**: カード（Card: 記述する媒体）、会話（Conversation: どう使われるかの説明）、確認（Confirmation: 受け入れ基準）
- 一般的な形式: 「[役割] として、[ゴール] を達成したい。それは [ビジネス価値] のためだ」＋受け入れ基準
- ビジネス・開発・テストの3つの視点で共同執筆し、共通の理解を作る（ブレーンストーミング、マインドマップ）
- 良いストーリーの条件 **INVEST**: 独立（Independent）、交渉可能（Negotiable）、価値がある（Valuable）、見積り可能（Estimable）、小さい（Small）、テスト可能（Testable）。ステークホルダーがテスト方法を思いつけないなら、ストーリーが不明確か価値を反映していない兆候

### 7.2 受け入れ基準

ステークホルダーが実装を受け入れるために満たすべき条件。テストケースで確認すべきテスト条件そのものとみなせる。

**用途**: スコープの定義、合意形成、ポジティブ・ネガティブ両方のシナリオの記述、受け入れテストのベース、計画と見積り

**書き方**
- **シナリオ指向**: BDD の Given / When / Then 形式
  - 例: Given 会員がカートに5,000円分の商品を入れている／When 購入手続きに進む／Then 送料が0円と表示される
- **ルール指向**: 箇条書きの検証リスト、入出力の対応表
- 明確で曖昧さがなければ独自形式でもよい

### 7.3 受け入れテスト駆動開発（ATDD）

テストファーストのアプローチ。ユーザーストーリーの実装前にテストケースを作る。

1. **仕様化ワークショップ**: 顧客・開発者・テスト担当者など異なる視点のメンバーで、ストーリーと受け入れ基準を分析・議論・記述する。不完全さや曖昧さはここで解消する
2. **テストケースの作成**: 受け入れ基準に基づいて作る（チーム全体でも、テスト担当者単独でもよい）。テストケースは「ソフトウェアがどう動くかの実例」であり、実例とテストケースは同じ意味で使われる
3. 作る順序: まず例外のない正常な流れ（ポジティブ）→ 次にネガティブ → 最後に非機能（性能効率性、使用性など）
4. 表現: ステークホルダーが理解できる自然言語で、事前条件・入力・事後条件を含める
5. テスト設計には第2〜6章の技法を適用できる。実行は手動でも自動でもよい

## 8. 技法の選び方［AL-TA 3.5］

### 8.1 テストベースの特徴から選ぶ

| テストベース（仕様）の特徴 | 第一候補 | 併用候補 |
| --- | --- | --- |
| 入力値の範囲・種類で処理が分かれる | 同値分割法 | 境界値分析 |
| 数値・日付・文字数の上下限がある | 境界値分析 | 同値分割法 |
| 複数の変数の式で判定される | ドメインテスト | — |
| 設定・環境・パラメーターの組み合わせが多い | 組み合わせテスト（ペアワイズ） | 同値分割法で値を絞る |
| 条件の組み合わせで結果が決まる業務ルール | デシジョンテーブルテスト | 境界値分析（条件の境界） |
| 状態によって反応が変わる、画面遷移、ライフサイクル | 状態遷移テスト | 境界値分析（ガード条件） |
| データを複数の機能が作成・更新・削除する | CRUDテスト | 状態遷移テスト |
| 業務フロー、ユースケース、エンドツーエンドの利用 | シナリオベースドテスト | デシジョンテスト、ラウンドトリップ |
| 期待結果が決められない（AI、検索、シミュレーション） | メタモルフィックテスト | ランダムテスト |
| 大量の入力で頑健性を見たい、ドメイン知識が少ない | ランダムテスト | メタモルフィックテスト |
| 仕様が乏しい、時間がない | 探索的テスト | エラー推測、チェックリスト |
| 繰り返し出る欠陥の型が分かっている | チェックリストベースドテスト、エラー推測 | — |
| ユーザーストーリーで開発している | ATDD、受け入れ基準 | 上記すべて |
| コードのテスト漏れを測りたい | ステートメント／ブランチテスト | MC/DC（安全重視） |

### 8.2 技法で狙える欠陥

- **データに基づく技法**: データ処理、ドメインの実装、ユーザーインターフェース、計算、パラメーターの組み合わせの欠陥
- **振る舞いに基づく技法**: 機能の欠落、伝達の欠陥、処理の欠陥など、ユーザー要求に関する欠陥
- **ルールに基づく技法**: ロジックと制御フローの欠陥

### 8.3 選定に影響する要因

| 要因 | 判断のしかた |
| --- | --- |
| テスト目的 | 何を評価したいかで決まる（工学の数値計算ならドメインテスト、与信判定ならデシジョンテーブル） |
| プロダクトリスク | リスクが高いほど強いカバレッジを要求する（例: ペアワイズではなく全組み合わせ）。リスクが低い、カバレッジを定義しにくい、日程が厳しいときは経験ベース |
| テストベース | モデルで書かれていればモデルベースの技法。オラクルが作れなければメタモルフィックや経験ベース |
| 既知の欠陥の型 | その型に強い技法（チェックリスト等）。前回効いた技法の再利用 |
| 担当者の知識と経験 | 不慣れな技法を重要な場面で使わない |
| 開発ライフサイクル | シーケンシャルなら形式的な技法、反復型なら軽量な技法（経験ベース）や設計の自動化 |
| 顧客・契約の要求 | 契約で指定されたテスト。顧客がシナリオで受け入れ基準を出すならシナリオベースド |
| 規制要件 | 例: ISO 26262 は ASIL に応じて同値分割法・境界値分析・エラー推測などを要求する |
| プロジェクトの制約 | 時間・予算が時間のかかる技法を制限する |

### 8.4 技法の組み合わせ例

- 状態遷移テストのガード条件に境界値分析を使う
- シナリオベースドテストの中の条件や変数の値をドメインテストで決める
- シナリオベースドテストにデシジョンカバレッジを組み合わせ、業務プロセス上の判定を網羅する（プロセスサイクルテスト）
- シナリオベースドテストにラウンドトリップカバレッジを組み合わせ、繰り返し発生する業務の流れのリスクに対応する
- メタモルフィックテストにランダムテストを組み合わせ、ソースとフォローアップを大量に生成する

### 8.5 テスト設計の自動化［AL-TA 3.5.2］

テストモデル（状態遷移モデルなど）を作り、ツールでテストウェアを生成する（モデルベーステスト）。

- **メリット**: モデル化で仕様の欠陥が見つかる、N スイッチや組み合わせなど複雑な基準を適用できる、選定基準が明確になる、繰り返し作業と保守が減る（モデルだけ直せばよい）、テストウェアの誤りが減る、レビューしやすい、トレーサビリティが上がる、多様な出力形式
- **リスク**: モデルに表れないテスト条件の見落とし、モデル保守工数の過小評価、ステークホルダーがモデルを理解しにくい、テスト自動化一般のリスク
