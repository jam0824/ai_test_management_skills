# 共通ルール

このプラグインのすべてのスキルが従う決まり。成果物を作る・直す・レビューする前に読む。

決まりの目的は2つある。**テストの説明責任**(どの要求・仕様から、どんなテストをして、どんな結果になったかを示せること)と、**トレーサビリティ**(どの成果物からでも、要求の側にもテスト結果の側にもたどれること)。迷ったら、この2つを満たすほうを選ぶ。

## 1. 成果物の置き場所

成果物は、テストする対象のプロジェクトの `テスト成果物/` に置く(テストマネージャーから別の場所を指定されたら、そこを使う)。

```
テスト成果物/
├─ テストレポート.html          最新のテストレポートへ飛ぶ入口(レポートを作ると、スクリプトが置く)
├─ 進行状況.md                  テストマネージャーが工程の状態を書く
├─ 質問表.md                    全工程で1つ
├─ 戻し記録.md                  「後からわかったこと」で戻った記録
├─ テストベースの写し/          取り込んだテストベースそのもの。次に変わったところを比べる相手(成果物としては読まれない)
├─ 01_要求仕様/                 要求.md、仕様.md
├─ 02_リスク分析/               リスク分析.md
├─ 03_テスト計画/               テスト計画.md
├─ 04_テスト分析/               テスト分析.md
├─ 05_テスト設計/               テスト設計.md
├─ 06_テスト実装/               ローレベルテストケース.md、テスト手順.md、テストデータ.md、テストデータ/、テストスイート.md、テスト環境.md、未実装.md
├─ 07_E2E自動テストスクリプト/  スクリプト一覧.md、未実装.md (スクリプト本体はプロジェクトのテスト用フォルダ)
├─ 08_テスト実行/               欠陥レポート.md、RUN-…/ (テストランごとの結果・証跡・セッションシート)
├─ 09_テストレポート/           判定.md、yyyyMMddHHmmss/ (レポート本体)、テストレポート.html (最新への入口)
└─ 結果まとめ/                  視認性アップで作るHTML(目次.html から開く)
```

視認性アップのHTMLは、工程のフォルダにも、その工程のページとして置かれる(`02_リスク分析/リスク分析.html` など)。成果物から作り直すものなので、直接書き換えない。

各工程のレビュー結果は、その工程のフォルダの `レビュー結果.md` に置く。

## 2. IDと表の書き方

成果物は1件ずつIDを付け、Markdownの表に書く。スクリプトがこの表を読んで、紐づけの確認・HTML・テストレポートの集計を行うので、形を守る。

| 成果物 | IDの形 | 作る工程 |
|---|---|---|
| 要求 | `REQ-001` | 要求仕様整理 |
| 仕様 | `SPEC-001` | 要求仕様整理 |
| 質問 | `Q-001` | 全工程(質問表.md) |
| リスク | `RISK-001` | リスク分析 |
| テスト終了条件 | `EXIT-001` | テスト計画 |
| テストアプローチ | `TA-001` | テスト計画 |
| フィーチャー | `FT-001` | テスト分析 |
| テスト条件 | `COND-001` | テスト分析 |
| カバレッジアイテム | `CI-001` | テスト設計 |
| ハイレベルテストケース | `HTC-001` | テスト設計 |
| テストチャーター | `CH-001` | テスト設計 |
| ローレベルテストケース | `LTC-001` | テスト実装 |
| テストデータ | `TD-001` | テスト実装 |
| テスト手順 | `PROC-001` | テスト実装 |
| E2E自動テストスクリプト | `SCR-001` | E2E自動テストスクリプト作成 |
| テストセッションシート | `SES-001` | テスト実行 |
| 欠陥レポート | `BUG-001` | テスト実行 |
| 戻し記録 | `RB-001` | テストマネージャー |

表の決まり:

- **成果物を定義する表は、先頭の列の見出しを `ID` にする。** 1行が1件。同じIDを2か所で定義しない。
- 紐づけは、見出しが `ID` で終わる列(`要求ID` `仕様ID` `関連ID` など)に相手のIDを書く。複数あるときは `、` か `,` で区切る。**紐づけとして数えられるのは、この列に書いたIDだけ。** 備考などの文章の中に書いたIDは、参考として扱われ、紐づけにはならない。
- IDは一度付けたら変えない。消した成果物のIDは使い回さない。番号は3桁以上の連番にする。
- 定義ではなく、すでにある成果物について書く表(テスト結果、未実装の一覧、テストスイートなど)では、IDを書く列の見出しを `ローレベルテストケースID` のように `〜ID` にする。この列に書いたIDが定義されているかを、スクリプトが確かめる。テスト結果と未実装の表は、先頭の列をその `〜ID` にする。
- セルの中で改行したいときは `<br>` を使う。セルの中の `|` は `\|` と書く。
- 表に入りきらない詳しい内容(テスト手順の中身、欠陥レポートの再現手順など)は、表の下に `## PROC-001` のようにIDの見出しを立てて書く。
- 各工程のスキルに、その工程で書く表の列を示してある。列を足すのはよいが、示してある列は消さない・名前を変えない。

## 3. トレーサビリティ(必須)

成果物は、次のように前の工程の成果物に紐づける。**太字は必須**で、無いとエラーになる。

| 成果物 | 紐づける相手 |
|---|---|
| 仕様 | **要求** |
| リスク | 仕様(仕様に紐づかないリスクは、仕様IDの列に「なし」と書く) |
| テストアプローチ | **仕様 か リスク のどちらか**(両方が望ましい) |
| フィーチャー | **仕様** |
| テスト条件 | **フィーチャー**、**テストアプローチ**、仕様(利用の流れのテスト条件は要求)、リスク |
| カバレッジアイテム | **テスト条件** |
| ハイレベルテストケース | **テスト条件**、カバレッジアイテム |
| テストチャーター | **テスト条件** |
| ローレベルテストケース | **ハイレベルテストケース** |
| テスト手順、E2E自動テストスクリプト | **ローレベルテストケース** |
| テスト結果、証跡 | ローレベルテストケース(テスト結果の表の先頭の列) |
| テストセッションシート | **テストチャーター** |
| 欠陥レポート | **ローレベルテストケース か テストセッションシート**。影響する要求・仕様(`要求・仕様ID` の列。見つけたテストと違う要求・仕様の不具合のとき、またはスコープ外のとき) |
| 質問 | 出た工程と、関係する成果物(関連IDの列) |

紐づけが抜けている・切れている(相手のIDが定義されていない)ものは、レビューで P0 または P1 として扱い、必ず直す。

リスクの紐づけには注意がいる。テストレポートでは「そのリスクに**直接**紐づくテスト条件」のテストだけを、そのリスクのテストとして数える。テスト条件のリスクIDの列は、実際にそのリスクを確かめる条件にだけ書く。

仕様がまだ無い要求(質問表で確認中のもの)に関わる成果物は、次のように書く。回答が来て仕様ができたら、戻し方に沿って紐づけ直す。

- リスク: 仕様IDの列は「なし」にし、根拠に要求のIDと質問のIDを書く。
- テスト条件: 関係の近いフィーチャーに紐づけ、`要求・仕様ID` の列に要求のIDを書く。

## 4. コマンド

確認・HTML・集計は、プラグインに入っているスクリプトで行う。数えたり、紐づけを目で追ったりする代わりに使う(Python 3.9 以上。`python` が無ければ `python3`)。

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" check --stage <工程>
```

| コマンド | すること |
|---|---|
| `check [--stage <工程>]` | トレーサビリティと決まりを確かめる。エラーが0件になるまで直す。警告(下流がまだ無いもの、文章の中の定義されていないID)は、理由を確かめる。`--stage` を付けると、その工程より下流に残っているエラーは分けて出る |
| `impact <ID> …` | そのIDを変えたときに影響を受ける下流のIDを出す。質問のIDを渡すと、その質問の回答を待っている成果物と、その下流を出す |
| `html [--stage <工程>]` | 視認性アップ。成果物をHTMLにする |
| `new-run` | 新しいテストランのフォルダを作り、テストランのIDを出す |
| `e2e-results --run <ID> --json <ファイル>` | PlaywrightのJSONレポートを、idごとのテスト結果の表にする |
| `metrics [--json]` | テストレポートに載せる数字を、成果物から数え直す(下の表) |
| `report` | テストレポート(HTML)を作る |

`<工程>` は `requirements` `risk` `plan` `analysis` `design` `implementation` `e2e` `execution` `report` のどれか。

`metrics` が数えるのは次のもの。テスト終了条件は、できるだけこの数字で判定できる形で書く(ここに無いものは、テストレポートで手で数えることになる)。`metrics` は終了条件の判定そのものはしない。

| 数えるもの | 中身 |
|---|---|
| テストケース | ローレベルテストケースの数、Pass・Fail・ブロック・未実行の数、実行率(Pass + Fail ÷ 総数)、未実装のハイレベルテストケースの数 |
| 要求・仕様・リスクごと | 直接紐づくテスト条件からたどったテストの、Pass・Fail・ブロック・未実行・未実装・セッション・不具合の数と状態(まったくテストしていない / 一部しか実行していない / 実行したがFailあり / すべて実行してすべてPass)。状態は Fail が先に立つので、Fail があっても実行していないテスト(未実装・未実行・ブロック・セッションの無いテストチャーター)が残っていることは、別に「残り」の数で出す |
| テストチャーターごと | セッションの「かかった時間(分)」の合計が、時間枠に達したか |
| 不具合と質問 | 修正されていない不具合(重要度つき)、未回答の質問 |
| テスト対象の版 | 今の版(実行情報.md に版が書かれた、いちばん新しいテストランの版)と、今の版で確かめていない結果(前の版や、版が書かれていないテストランの Pass・Fail をそのまま数えているテストケース) |

成果物の場所が `./テスト成果物` でないときは `--root <フォルダ>` を付ける。

## 5. 質問表

質問表は全工程で1つ(`テスト成果物/質問表.md`)。仕様から決められないことは**推測で決めず**、ここに書く。推測で決めた期待結果でテストが Pass しても、何も確かめたことにならないため。

```markdown
| ID | 工程 | 質問 | 関連ID | 種類 | 回答が必要な理由 | 実機の動き | 状態 | 回答 |
|---|---|---|---|---|---|---|---|---|
| Q-001 | テスト分析 | 小数の年齢を入力したときの扱いは？ | SPEC-001、COND-004 | 曖昧 | 期待する結果が決まらない | | 未回答 | |
```

- **工程**: 質問が出た工程の名前(要求仕様整理、リスク分析、テスト計画、テスト分析、テスト設計、テスト実装、E2E自動テストスクリプト作成、テスト実行)。
- **関連ID**: どの要求・仕様の問題か、影響を受ける成果物はどれか。
- **種類**: 曖昧 / 矛盾 / 抜け / テストしにくい / その他。
- **実機の動き**: テスト対象を動かして見た、今の動き。`observe-actual-behavior`(実機確認)のスキルだけが書き、ほかの工程では空のままにする(例: `17.5 を入れると 17 として登録される。証跡: RUN-20261123-150000/証跡/Q-001_1.png`)。答える人が「その動きで正しい・正しくない」を選べるようにするための情報で、**期待値ではない**。この列の内容を、期待結果や合否の基準に写さない。
- **状態**: 未回答 → 回答済み(人が答えた) → 反映済み(成果物に反映した)。
- 書く前に、同じ質問がすでに無いかを確かめる。
- 質問に答えるのは人。聞くのはテストマネージャーなので、ほかのエージェントは質問表に書いて、報告に質問のIDを入れる。
- 回答を待つ成果物は、回答待ちであること(と質問のID)がわかるようにして、先へ進める。`状態` の列があれば `回答待ち(Q-001)`、無ければ `備考` に質問のIDを書く。
- **回答待ちにしたテストケースは、回答が来るまで実装も実行もされない。** 回答待ちにするのは、テストベースから期待結果や合否の基準を決められないときだけにする。テストベースから決められる部分があれば、その部分で決めて進める(例: 注意書きの「各点の意味が読み取れる文が画面にある」までは仕様書から決まる)。回答で基準が変わるかもしれないときは、`状態` は決まった状態(`設計済み` など)のままにし、`備考` に「Q-001 の回答で基準が変わりうる」と書く。回答が来たら、戻し方に沿って見直す。
- 前の工程で出た質問の回答を待つときは、同じ質問を新しく書かない。待つ成果物の `状態` か `備考` に、その質問のIDを書くだけでよい。`impact Q-001` で、その質問を待っている成果物を出せる。
- 中身が回答待ちで決まらない項目(境界の値、テストオラクルの中身など)は、わかっている範囲で書き、決まっていない部分を「Q-001 の回答待ち」と書く。値を推測で埋めない。

## 6. 後からわかったことの扱い

前の工程で決めることが後からわかったら、**見つけた工程で前の工程のドキュメントに書き足して済ませない**。テストマネージャーに報告し、テストマネージャーがその工程まで戻ってやり直す。書き足しで済ませると、その工程のレビューを通らない内容が混ざり、下流への影響も追えなくなる。

| わかったこと | 決める工程 |
|---|---|
| 要求・仕様 | 要求仕様整理 |
| リスク | リスク分析 |
| テストアプローチ、テスト終了条件 | テスト計画 |
| テスト条件、テストオラクル | テスト分析 |
| ハイレベルテストケース、実施方法、テストチャーター | テスト設計 |
| ローレベルテストケース、テストデータ、テスト環境、テスト手順 | テスト実装 |
| E2E自動テストスクリプト | E2E自動テストスクリプト作成 |

報告には「何がわかったか」「どの成果物(ID)に関わるか」「どの工程で決めることだと考えるか」を書く。自分の工程の成果物は、わかる範囲で進めておく。

### やり直しを任されたとき

テストマネージャーから、戻しによるやり直しを任されたときは、次のようにする。

- 直すのは、伝えられた変更と、その影響を受ける部分だけ。関係のない部分を作り直さない(レビュー済みの内容が変わり、下流への影響が追えなくなるため)。
- すでにあるIDは変えない。新しく足すものには、続きの番号を付ける。IDではない連番(テストスイートの「順番」など)は振り直してよい。振り直したら、その番号を指している文も直す。
- 変えた内容と、前の工程の成果物の言い方がずれることがある。中身が食い違うときは報告する(テストマネージャーが、その工程に戻すかを決める)。言い方だけのずれは直さず、報告に書くだけでよい。
- 要らなくなった成果物は行を消し、消したIDを報告する。下流の成果物が、消したIDに紐づいたまま残るため。
- 変えた・足した・消したIDを、報告に書く。テストマネージャーが、次の工程に何をやり直させるかを決めるのに使う。

## 7. 作成スキルが終わるときの報告

作成スキルは、終わる前に `check --stage <自分の工程>` を実行し、エラーを0件にする。やり直しで前の工程の成果物を変えたときは「下流の工程に残っているエラー」が出ることがある。これは自分では直さず、報告に書く(テストマネージャーが、下流の工程をやり直させて直す)。そのうえで、テストマネージャー(単独で使われたときは依頼した人)に次のことを報告する。

1. 作った・変えたファイル
2. 質問表に書いた質問のID
3. 前の工程で決めること(上の6の報告)。無ければ「なし」
4. 確かめたこと(check の結果)と、できなかったこと・確かめていないこと

できていないことを、できたと書かない。

## 8. レビューの進め方

レビューはテストマネージャーが行う。作ったエージェントとは別の目で見るためなので、作ったエージェント自身に任せない。

1. レビューする成果物と、その作成スキルが使ったのと同じ入力を読み、照らし合わせる。
2. `check --stage <工程>` を実行する。エラーは P0 か P1 の指摘にする。警告は1件ずつ理由を確かめる。
3. その工程のレビュースキルの「見ること」に沿って確かめる。
4. 指摘に優先度を付けて列挙する。
   - **P0**: そのままでは次の工程に進めない(必要な成果物が無い、仕様と大きく食い違う、紐づけが切れて追えない)
   - **P1**: 直さずに進むとテストの信頼を損なう(リスクの高いところの抜け、推測で決めた期待結果、紐づけの抜け、テストベースから決められるのに回答待ちにしていて要求やリスクがテストされなくなるもの、試した値が出力まで届かず何も確かめていないテストケース)
   - **P2**: 使えるが、直したほうがよい
   - **P3**: 好みの範囲
5. P0 と P1 を直す。直すのは、その工程の作成スキルを使うエージェントである(指摘とIDを伝えて、やり直しを任せる)。レビューした側が直すと、作る目とレビューする目が分かれなくなるため。言い回しや誤字のように中身が変わらない直しだけは、レビューした側が直してよく、`対応` に「レビューで直した」と書く。原因が前の工程にある指摘は、ここで直さず「6. 後からわかったことの扱い」に乗せる。情報が無くて直せない指摘は、質問表に書き、該当する成果物を回答待ちにする(「5. 質問表」のとおり、テストベースから決められる部分は決めて進める)。
6. 直したら、もう一度最初からレビューする。P0 と P1 が無くなるまで繰り返す。
7. 結果を、その工程のフォルダの `レビュー結果.md` に書く。

```markdown
# <工程>のレビュー結果

## レビューした成果物と照らし合わせた入力

## 経過
| 回 | P0 | P1 | P2 | P3 | したこと |
|---|---|---|---|---|---|

## 指摘
| 回 | 優先度 | 場所 | 指摘 | 対応 |
|---|---|---|---|---|

## 残っていること
(直していない P2・P3、質問表に回したこと、戻し方に乗せたこと)
```

`対応` には「直した」「戻し方に乗せた(RB-xxx)」「質問表に書いた(Q-xxx)」「直していない(P2)」のように書く。
