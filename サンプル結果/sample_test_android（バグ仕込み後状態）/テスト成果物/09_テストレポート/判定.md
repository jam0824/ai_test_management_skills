## 足りないこと

- **EXIT-003**: BUG-001 と BUG-002 を直して確認テスト(LTC-033、034、036、038 の再実行)を行う。ただし BUG-001 は Q-028(取り崩しに税金をかけるのが仕様か)の回答で不具合でなくなりうる。仕様だった場合も、BUG-002(投資残高がマイナスになる)は別に直す必要がある。
- **EXIT-004**: Q-027 に回答をもらい、許す件数を決める。いまの重要度が中の未修正は BUG-003(削除で押した行でなく最後の行が消える)、BUG-008(カンマ区切りの金額が先頭の数字だけで計算される)、BUG-010(開始年齢にとても小さい値を入れるとアプリが応答しなくなる)の 3 件。
- **EXIT-006**: 高リスクに紐づく未実装のハイレベルテストケースを実装・実行する。そのためには Q-002〜Q-007、Q-009、Q-012、Q-013、Q-022、Q-025 の回答が要る。高リスクに紐づく未実装は HTC-021、022、023(RISK-005)、HTC-027(RISK-007)、HTC-035〜038(RISK-001、002)、HTC-045、047(RISK-010)、HTC-051(RISK-011、012)の11件。
- EXIT-006 の測り方について: `metrics` は Fail があるリスクを「実行したがFailあり」と表示するため、未実装が残っていても「一部しか実行していない」にならない。測り方の字面どおりに数えると 0 件になるが、終了条件の文(紐づくテストをすべて実行した)とテスト計画の備考に従い、各リスクの未実装の数で判定した。

## テスト計画からの変更

- 対象外にしたもの(テスト計画のとおり): Android 8.0(API 26)〜13(API 33)での動作(RISK-039 が残る)、注意事項を画面に出すこと(RISK-040、Q-026 の回答待ち)、性能(応答時間)。
- 回答待ちでハイレベルテストケース 19 件(HTC-011、021、022、023、027、029、034、035、036、037、038、045、046、047、051、056、064、068、070)を実装していない。このため、**1円単位の手取り(税・社会保険料の計算)、期間が切り替わる境界の月の収入・生活費、シミュレーションの終了年齢(Q-001)、イベントの金額、取り崩しの基準などは確かめていない。** これらは「年収÷12 を超えない」「年収を増やすと減らない」などの性質でしか確かめておらず、性質を満たす範囲の計算の誤り(税率表の誤りなど)は見つけられない。
- 探索的テストで出たチャーター案のうち、全角数字の入力、試していない欄の負の値・極端な値、給与変更10件すべてに値を入れたテストは見送った(SES-002、SES-003、SES-008 のデブリーフィング)。これらのふるまいは確かめていない。
- 初期値のテストを1件(HTC-001 → LTC-001)にまとめたため、実際に仕様書と違ったのは現役時生活費(SPEC-013、BUG-005)だけなのに、SPEC-004〜SPEC-018 の15件がすべて「実行したがFailあり」と数えられている(08_テスト実行/レビュー結果.md の P2)。SPEC-013 以外の初期値14項目は、LTC-001 の証跡では仕様書と一致していた。
- E2E自動テストは、利用者と違う読み取り用の表示(wm size 1080x6000、密度160)で動かした。見た目(標準の表示で結果が読めるか、スクロール、回転)の判定は、標準の表示での手動テストで行った。E2E の Pass は、標準の表示での見え方を保証しない。
- 戻し記録 RB-001〜RB-004: テストウェアの誤りを直して実行し直した。RB-001 は HTC-050 の入力欄と基準の向きの誤り(テスト実装で発見)。RB-002(LTC-027 の丸めの許容)、RB-003(LTC-037 の取り崩しの確かめ方)、RB-004(LTC-065 のスクリプトが横向きで止まる)は、テスト実行で Fail になったのがテストウェアの誤りだったもので、直して RUN-20261123-203835 で実行し直し、3件とも Pass になった。

## テストの妨げになったことと対処

- エミュレータの不調: RUN-20261123-104110 の実行中に、エミュレータのシステムの Watchdog 停止、アプリ・Launcher・System UI の ANR、uiautomator dump が取れない状態が何度も起きた。エミュレータを再起動(2回目はコールドブート)し、途中で止まった E2E 29件を流し直し、さらに5件を流し直した。BUG-010 の ANR(開始年齢にとても小さい値)はアプリの不具合と判断したが、**それ以外の ANR がアプリ起因かどうかは判断できていない。**(08_テスト実行/RUN-20261123-104110/実行情報.md)
- 回答が来なかった質問: 質問 29 件(Q-001〜Q-029)がすべて未回答。要求仕様整理で26件、テスト計画で1件、テスト実行で2件出た。回答待ちのまま進めたため、19件のハイレベルテストケースを実装できず、EXIT-004 を判定できず、BUG-001・BUG-004・BUG-011 が不具合かどうかが確定していない(BUG-001 は Q-028、BUG-004・BUG-011 は Q-029)。
- テスト環境が emulator-5554(Android 14 / API 34)の1台だけだった。

## 次のテストに向けた教訓

- 質問 29 件のうち 26 件が要求仕様整理で出た(計算式・境界・終了年齢・正しくない入力の扱い)。仕様書の計算の部分が足りないことは最初の工程でわかっていたので、テスト設計より前に回答をもらう段取りにすれば、未実装の 19 件と EXIT-006 の不足を減らせる。
- 初期値のように独立した項目を1件のテストケースにまとめると、1項目の違いで紐づく仕様すべてが Fail と数えられる。仕様ごとの状態を正しく数えたいときは、項目ごとにテストケースを分ける。
- テスト実行で Fail になった 15 件のうち 3 件(LTC-027、037、065)はテストウェアの誤りだった(RB-002〜004)。丸めの許容や入力の確かめのような「期待値の周りの条件」をテスト実装のレビューで具体的な値で確かめる。
- エミュレータ1台(メモリ 2GB)で長時間の E2E を流すと不調が続いた。メモリを増やすか、途中でエミュレータを再起動する段取りにする。
- EXIT-006 のように「未実装が残ること」を判定する終了条件は、`metrics` の状態の名前(Fail があると「実行したがFailあり」になる)ではなく、未実装の件数で測る形に書く。
