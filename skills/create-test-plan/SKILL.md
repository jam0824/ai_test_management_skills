# テスト計画

あなたはテスト計画エージェントとして、テスト全体をどんなアプローチで行うかを決める。対象はシステムテストのレベルである。詳しいテストケースはここでは作らない。ここで決めるのは、テスト全体の進め方と、「どうなったら終わりと言えるか」である。

最初に共通ルール `${CLAUDE_PLUGIN_ROOT}/shared/conventions.md` を読む。

## 入力

- `テスト成果物/01_要求仕様/要求.md`、`仕様.md`
- `テスト成果物/02_リスク分析/リスク分析.md`
- `テスト成果物/質問表.md`

## 進め方

### 1. テスト目的・テストアイテム・スコープを決める

- **テスト目的**: このテストで何を確かめ、誰に何を示すのか。要求をもとに書く。
- **ドキュメント**: 参照した資料と成果物。
- **テストアイテム**: テストする対象(アプリ、画面、機能、版)。
- **テストスコープ**: テストアイテムのうち、今回テストする範囲。
- **対象外/制約**: テストしないものと理由、テストの制約(環境、時間、使えるツール)。リスクが高いのに対象外にするものは、理由と、残るリスクを書く。

### 2. テスト終了条件を決める

テスト終了条件は、テストレポートで「満たした / 満たしていない」を判断するのに使う。だから、**数字など測れる形**で書き、測り方も書く。

- 例: 「テストケースの実行率が100%」「重要度が高の修正されていない不具合が0件」「高いリスクに紐づくテストケースがすべて実行済み」
- 「十分にテストした」「品質に問題がない」のような、人によって判断が変わる書き方はしない。
- 根拠になる要求・仕様やリスクから決められない基準(どこまでの不具合を許すか、など)は、推測で決めず質問表に書く(工程は「テスト計画」)。その終了条件の `備考` には、回答待ちであることと質問のidを書いておく。

### 3. テストアプローチを決める

どのようなアプローチでテストするかを、テストタイプで整理する。

- **テストタイプ**: 機能テスト、セキュリティテスト、ユーザビリティテスト、性能テスト、互換性テストなど。仕様とリスクから、必要なものを選ぶ。
- **実施方法**: E2E自動テスト / 手動テスト / 探索的テスト。自動テストはE2E自動テストだけにする(ユニットテストなどは今回の対象外)。
  - 手順と期待結果がはっきり決まり、繰り返し実行したいもの → E2E自動テスト
  - 人の目で見て判断するもの、自動化が割に合わないもの → 手動テスト
  - 仕様が薄い、リスクが高く想定外の動きを探したい、使われ方が幅広いもの → 探索的テスト
- **内容**: 何を、どんな考え方で確かめるかを1〜2文で書く。
- 根拠になる仕様と、対応するリスクのidを書く。**高いリスクには、必ず1つ以上のアプローチを紐づける。**

1つのアプローチに何でも入れない。テストタイプか実施方法が違えば、行を分ける。

## 出力

`テスト成果物/03_テスト計画/テスト計画.md`

```markdown
# テスト計画

## テスト目的
## ドキュメント
## テストアイテム
## テストスコープ
## 対象外/制約

## テスト終了条件

| ID | 終了条件 | 測り方 | 備考 |
|---|---|---|---|
| EXIT-001 | テストケースの実行率が100% | 実行した(Pass + Fail)テストケース数 ÷ ローレベルテストケースの総数 | |
| EXIT-002 | 重要度が高の修正されていない不具合が0件 | 欠陥レポートのうち、重要度が高で状態がクローズでも却下でもないものの件数 | |
| EXIT-003 | 重要度が中の修正されていない不具合が、決められた件数以下 | 欠陥レポートのうち、重要度が中で状態がクローズでも却下でもないものの件数 | 基準の件数は Q-007 の回答待ち |

## テストアプローチ

| ID | テストタイプ | 実施方法 | 内容 | 仕様ID | リスクID |
|---|---|---|---|---|---|
| TA-001 | 機能テスト | E2E自動テスト | 年齢の入力チェックを、境界と異常な入力を中心に確かめる | SPEC-001、SPEC-002 | RISK-001 |
| TA-002 | 機能テスト | 探索的テスト | 登録まわりを、仕様に書かれていない入力や操作の順番で探索する | SPEC-001 | RISK-001 |
```

## 終わる前に

- `python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" check --stage plan` を実行し、エラーを0件にする。
- 高いリスクのすべてにアプローチが紐づいているか、スコープに入れた仕様のすべてにアプローチがあるかを確かめる。
- 終了条件を1つずつ読み、テストが終わったときに数字で判断できるかを確かめる。
- 共通ルールの「作成スキルが終わるときの報告」の4点を報告する。
