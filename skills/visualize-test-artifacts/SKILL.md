# 視認性アップ

成果物のMarkdownは、エージェントとスクリプトが読むための形になっている。人が読むには、紐づけをたどれるHTMLのほうが把握しやすい。このスキルは、成果物をスクリプトでHTMLにする。

HTMLは成果物から作り直すものなので、**HTMLを直接書き換えない**。中身を変えたいときは成果物を直して、もう一度作る。

## 作り方

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" html --stage <工程>
```

`--stage` を省くと、全部の工程のページを作り直す。成果物の場所が `./テスト成果物` でないときは `--root <フォルダ>` を付ける。

ページは2か所にできる。人は工程のフォルダを開いて結果を探すので、工程のフォルダにも置く。

- `テスト成果物/結果まとめ/`: 目次・ID索引と、すべての工程のページ(`リスク分析.html` など、工程の名前)
- 工程のフォルダ: その工程のページ(`02_リスク分析/リスク分析.html` など)。中身は結果まとめのものと同じで、メニューとIDのリンクは結果まとめのページへ飛ぶ。フォルダがまだ無い工程には作らない

| 工程 | `--stage` | ページでわかること |
|---|---|---|
| 要求仕様整理 | `requirements` | 要求の一覧。行を開くと要求のほかの欄と、紐づく仕様が出る。仕様が無い要求(質問表に書いてあるか)、要求に紐づかない仕様 |
| リスク分析 | `risk` | リスクの一覧。リスクレベルの高い順。行を開くと根拠・備考と、紐づく仕様とその要求が出る |
| テスト計画 | `plan` | テストアイテムとテストスコープ(上に出す)。テスト終了条件。テストアプローチが要求・仕様・リスクを満たしている割合(満たしていないものと理由: 対象外にした理由、仕様が無い要求を扱うリスク、テストアプローチが無い)。テストアプローチ(テストタイプ・内容・実施方法と、紐づく要求・仕様・リスク) |
| テスト分析 | `analysis` | フィーチャーごとのテスト条件と、紐づくテストアプローチ・リスク・優先順位・テストオラクル。テスト条件のカバレッジ(要求・仕様・リスク・テストアプローチを押さえている割合と、押さえていないものの理由。要求・リスク・テストアプローチから、開いてテスト条件までたどれる一覧) |
| テスト設計 | `design` | テストケースのカバレッジ(要求・仕様・リスク・テスト条件・カバレッジアイテムを押さえている割合と、押さえていないものの理由。テスト条件・要求から、開いてテストケース・テストチャーターまでたどれる一覧)。テスト条件ごとの技法とカバレッジ(通る数 / 出した数)。テストチャーター(開くと対象の領域・時間枠・してはならないこと) |
| テスト実装 | `implementation` | ローレベルテストケースのカバレッジ(要求からハイレベルテストケースまでを押さえている割合と、押さえていないものの理由。未実装・回答待ちの理由と、どのテスト条件で止まっているか。テスト条件・要求から、開いてローレベルテストケースまでたどれる一覧)。ローレベルテストケース(開くと入力・期待値などと、もとのハイレベルテストケース・テスト手順)。未実装のテストケースと理由 |
| E2E自動テストスクリプト作成 | `e2e` | E2E自動テストスクリプトのカバレッジ(E2E自動テストのローレベルテストケースにスクリプトがそろった割合と、そろっていないものの理由。テスト名から出どころの成果物を上へ、要求からスクリプトまで下へ、開いてたどれる一覧)。自動化できなかったテストケースと理由 |
| テスト実行 | `execution` | タブで切り替える。まとめ(件数、実施方法ごとの内訳、探索的テストのチャーター・セッション・時間・不具合、要求・リスクから開いて結果までたどれる一覧)、Fail(最新の結果が Fail のテストケースだけ)、E2E自動テスト・手動テスト(テストケースごとの結果。開くと証跡・欠陥レポート)、探索的テスト(セッション。開くとチャーター・不具合・セッションシート)、欠陥レポート(開くと、期待値と実際の結果を並べ、その下に再現手順。原因・証跡(ファイルへのリンク)・見つけたテスト・影響する要求とリスク・メモなどはたたんで出る。`欠陥レポート.md` の節の「- 項目名: 内容」を項目として読む)、質問・ドキュメント |

どのページにも、その工程で出た質問(行を開くと、種類・理由・回答と関連するものが出る)と、その工程のドキュメントの中身が入る(テスト実行のページは「質問・ドキュメント」のタブの中)。あわせて次の2つができる。

- `結果まとめ/目次.html`: 目次と、トレーサビリティの確認の結果(エラーと警告)。テストレポートがあれば、いちばん上に最新のレポートへのリンクが出る(成果物のフォルダ直下の入口 `テストレポート.html` も作り直す)
- `結果まとめ/ID索引.html`: ID索引。成果物1件ごとに、中身と、上流(要求の側)・下流(テスト結果の側)の紐づけが載る。ページの中のIDは、すべてここへのリンクになる

## 作ったあとに確かめること

- コマンドの出力に出た「開くページ」を伝える。ブラウザを操作できるツールがあれば、実際に開いて表示を確かめる。
- 表が空、または成果物が載っていないときは、成果物の表の形が共通ルール(`${CLAUDE_PLUGIN_ROOT}/shared/conventions.md` の「2. IDと表の書き方」)に合っていないことが多い。`python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" check` でエラーを見て、成果物の表の形を直す(先頭の列の見出しが `ID` か、IDの形が合っているか)。中身は変えない。
- `目次.html` にエラーが出ているときは、紐づけの抜け・切れがある。テストマネージャーに報告する。

テストレポートは、レポートそのものが人向けのHTMLなので、ここでは作らない(`create-test-report` スキルが作る)。
