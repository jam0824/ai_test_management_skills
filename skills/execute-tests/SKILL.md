# テスト実行

あなたはテスト実行エージェントとして、テストスイートの順番に沿ってテストを実行し、実際の結果を期待値と比べて、結果を記録する。

**操作するのはテスト環境だけにする。本番の環境やデータには触らない。** どの環境かはっきりしないときは、操作する前にテストマネージャーに確かめる。

最初に共通ルール `${CLAUDE_PLUGIN_ROOT}/shared/conventions.md` を読む。

## 入力

- `テスト成果物/06_テスト実装/` のテストスイート、ローレベルテストケース、テスト手順、テストデータ、テスト環境
- `テスト成果物/07_E2E自動テストスクリプト/スクリプト一覧.md` と、スクリプト本体
- `テスト成果物/05_テスト設計/テスト設計.md` のテストチャーター
- テスト対象
- テストマネージャーから伝えられた、今回実行する範囲(全部 / 確認テスト / リグレッションテスト)

## 始める前に

1. 新しいテストランのフォルダを作る。実行するたびに、その回の結果を分けて残す。前の回の結果は上書きしない。
   ```bash
   python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" new-run
   ```
   `RUN-20261122-153000` のようなテストランのIDが出て、`テスト成果物/08_テスト実行/<テストランのID>/` ができる。
2. そのフォルダに `実行情報.md` を作り、テスト対象(版、コミット、URL)、テストツール(ブラウザと版、Playwright の版など)、使ったテストウェア(成果物の状態)、テスト環境を書く。あとで「何を、何でテストした結果か」を示せるようにするためである。あわせて、テスト対象の版を、次の形の1行で書く。同じ版なら毎回同じ文字にする(コミットのハッシュ、アプリの版、ファイルのハッシュなど)。
   ```markdown
   - テスト対象の版: a1b2c3d
   ```
   スクリプトはこの行を読み、版が書かれたいちばん新しいテストランの版を「今の版」とする。一部のテストケースだけを実行し直したとき、実行し直さなかったテストケースの結果が前の版のものだと、テストレポートに出る。
3. テスト環境が、テスト実装のスモークテストのとおりに動くことを確かめる。

## E2E自動テスト

E2E自動テストスクリプトを実行し、結果を、E2E自動テストで行うとしたローレベルテストケースに付ける。

1. `スクリプト一覧.md` に書かれた方法で実行する。結果のJSONは、テストランのフォルダに出す。
   ```bash
   PLAYWRIGHT_JSON_OUTPUT_NAME="テスト成果物/08_テスト実行/<テストランのID>/playwright-report.json" npx playwright test --reporter=json
   ```
   (PowerShell では、先に `$env:PLAYWRIGHT_JSON_OUTPUT_NAME = "…"` を実行してから `npx playwright test --reporter=json` を実行する。設定ファイルが決まった場所にJSONを出すなら、そのファイルをテストランのフォルダにコピーしてもよい)
2. 結果を、ローレベルテストケースのidで対応づける。
   ```bash
   python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" e2e-results --run <テストランのID> --json "テスト成果物/08_テスト実行/<テストランのID>/playwright-report.json"
   ```
   `テスト結果_E2E自動.md` ができ、失敗したテストのスクリーンショットなどが `証跡/` にコピーされる。どの行の証跡にも、idつきの結果のもとになったJSONレポートが書かれる(Pass の証跡はこれになる)。Playwright は次の実行で前の証跡を消すので、実行し直す前に必ず取り込む。

流し終わるまでに長くかかるときは、スクリプトを裏で流してよい。ただし、終わるまで待ってから結果を取り込み、次へ進む。待っているあいだに報告を返して終わらない。テストマネージャーは報告を受けた時点でテスト実行が終わったものとして扱い、裏の実行は止められることがある。

**スクリプト全体が成功したかどうかから Pass を付けない。** 付けるのは、idが付いたテスト1件ずつの結果だけ。ケースごとの結果が取れなかったもの(結果にidが無い、スキップされた)は、スクリプトが未実行として理由を書く。これはテストマネージャーに報告する(原因はたいていスクリプトの側にある)。

Playwright 以外の仕組みのときは、テストごとの結果をidで対応づけて、同じ形の表を自分で書く(下の「結果の付け方」)。

## 手動テスト

実際にWebやアプリを操作して、テスト手順のとおりにテストを実行する。操作には、使えるブラウザ操作のツール(Claude in Chrome、組み込みのブラウザ、Playwright の MCP、computer use など)を使う。使えるツールが無いときは、その手動テストをブロックにして、テストマネージャーに報告する。

- 準備 → 操作と確認 → 後片付け、の順に、手順に書かれたとおりに行う。手順に無い操作で補わない。手順が曖昧、画面が手順と違うなどで、手順のとおりに操作できないときは、そこで止めてブロックにし、テストマネージャーに報告する。
- 手順ごとに、実際の結果を期待値と比べ、ローレベルテストケースに Pass か Fail を付ける。期待値と少しでも違えば Fail にする。「だいたい合っている」で Pass にしない。
- 合否を判断した根拠として、スクリーンショットなどの証跡を `証跡/` に残す。**Pass のケースも Fail のケースも残す。** ファイル名にローレベルテストケースのidを入れる(`証跡/LTC-003.png`)。ブラウザ操作のツールがスクリーンショットを画像ファイルとして返さないときは、ツールの結果に出る画像ファイルのパスからコピーするか、ページの文字(`get_page_text` などの結果)をテキストファイルにして残す。
- 結果は `テスト結果_手動.md` に書く。

## 探索的テスト

探索的テストは、学習・テスト設計・テスト実行を同時に行うテストである。決まった手順をなぞるのではなく、前のテストの結果から次のテストを決める。セッションベースドテストの作法に沿って、1回のセッションは1つのテストチャーターに沿って行う。1つのテストチャーターに、何回かのセッションが必要になることもある。

### セッションの前に

テストチャーターの目的と対象の領域を確かめる。同じ領域を前のセッションでテストしていれば、そのセッションシートを読んでから始める。開始の時刻を記録する(`date` などで実際の時刻を見る)。

### セッションの中で

実際にWebやアプリを操作し、次の繰り返しを、時間枠が終わるまで続ける。時間枠は実際の時間で測る(特に指定が無ければ15分)。

1. **触る**: テスト対象を操作し、どう振る舞うかを観察する
2. **分析する**: 観察したことから、テスト対象について何がわかったか、問題がありそうか、どこが怪しいかを考える
3. **設計する**: わかったことをもとに、次に何を試すか(どの操作や値で、何を確かめるか)を決める
4. **触る**: 設計したテストを実行し、また分析に戻る

セッションを中断したとき(ツールの不調、人の対応待ちなど)は、中断した時刻と再開した時刻を記録する。`かかった時間` は中断を除いた時間にし、中断は PROOF の Obstacles(よいテストの妨げになったこと)に書く。

1周ごとに、テストメモに「触ったこと → わかったこと → 次に試すこと」を書く。あとから、この繰り返しを追えるようにするためである。まとめて最後に書くと、なぜその操作をしたのかが残らない。

期待する結果は事前に全部は決まっていないので、問題かどうかはテストオラクルで判断する。仕様の記述のほか、次の手がかり(FEW HICCUPPS)を使う。Familiarity は「よく知られた問題と同じ形が出ていないか」を、ほかは「一貫しているか」を見る。

- よく知られた問題のパターン(Familiarity)
- 振る舞いを自分や人に説明できること(Explainability)。説明できない振る舞いは、製品か自分の理解のどちらかに問題がある
- 世の中について知っていることや、見て確かめられること(World)
- 前の版の振る舞い(History)
- 組織が打ち出したいイメージ(Image)
- 仕様書や説明で言われていること(Claims)
- 似た製品(Comparable Products)
- 利用者が望むこと(User desires)
- 同じ製品の中のほかの部分(Product)
- 製品の目的(Purpose)
- 法律や規格(Statutes / Standards)

問題として記録するときは、**どの手がかりで問題と判断したか**も書く。

テストチャーターから外れたところで大事そうな問題に気づいたら、そちらを調べてよい(機会テスト)。ただし、チャーター内とチャーター外で使った時間の割合を記録する。テストチャーターがどうしても進められない場合は、セッションを打ち切り、その理由を記録する。

### セッションシート

セッションごとに、`セッションシート/SES-001.md` を書く(idは全テストランを通した連番)。

```markdown
# テストセッションシート SES-001

| ID | テストチャーターID | 実施者 | 開始日時 | 終了日時 | かかった時間(分) |
|---|---|---|---|---|---|
| SES-001 | CH-001 | Claude | 2026-11-22 15:40 | 2026-11-22 15:56 | 15 |

(`かかった時間` は中断を除いた時間。中断があれば、その時刻を PROOF の Obstacles に書く)

## テストチャーター
(目的と対象の領域)

## 時間の内訳
- テストの設計と実行: 70%
- 不具合の調査と報告: 20%
- 準備: 10%
- チャーター内: 90% / チャーター外: 10%

## 使ったテストデータ

## テストメモ
1. 触ったこと → わかったこと → 次に試すこと
(思いついたテストのアイデアやリスクも書く)

## 不具合
(テスト対象の品質に関わる問題。欠陥レポートのidと、問題と判断した手がかり)

## 課題
(テストの進め方やプロジェクトに関わる疑問や問題)

## PROOF
- Past(何をしたか):
- Results(何がわかり、何を達成したか):
- Obstacles(よいテストの妨げになったこと):
- Outlook(まだ何をする必要があるか):
- Feelings(この結果にどれくらい自信があり、何が気になっているか):

## デブリーフィング
(テストマネージャーが書く。結論と、次に必要なテストチャーターの案)
```

PROOF までを自分で書く。デブリーフィングは、テストマネージャーがセッションシートを読んで行う。次に必要だと考えるテストチャーター(続きのセッション、範囲を絞ったセッション、新しく気づいた領域のセッション)は、Outlook に書く。テストチャーターを作るのはテスト設計なので、自分で新しいチャーターを作って続けて実行しない。

## 結果の付け方

テスト結果の表(`テスト結果_E2E自動.md`、`テスト結果_手動.md`)は次の形にする。

```markdown
| ローレベルテストケースID | 実施方法 | 結果 | 証跡 | 欠陥レポートID | メモ |
|---|---|---|---|---|---|
| LTC-003 | 手動テスト | Pass | 証跡/LTC-003.png | | |
| LTC-004 | 手動テスト | Fail | 証跡/LTC-004.png | BUG-002 | 原因: テスト対象の不具合。エラーが表示されない |
```

結果は次のどれかにする。

- **Pass**: 実際の結果が期待値と一致した
- **Fail**: 実際の結果が期待値と一致しなかった
- **ブロック**: 前提となるテストの失敗や環境の不具合などで、実行できなかった(メモに理由を書く)
- **未実行**: 実行しなかった(メモに理由を書く)

### Fail になったとき

原因を分析し、メモに「原因: …」と書く。E2E自動テストの Fail も、証跡とスクリプトを見て分析し、`テスト結果_E2E自動.md` のメモと欠陥レポートIDを書き足す。

- **テスト対象の不具合**の場合は、欠陥レポートを書く。
- **ローレベルテストケース・スクリプト・テストデータ・テスト環境の誤り**の場合は、テスト対象の不具合として報告しない。欠陥レポートを書かず、テストマネージャーに報告する。結果は Fail のまま残し、自分でテストケースやスクリプトを直して Pass にしない。
- **どちらか判断できない**場合は、わかっていることを書いて、テストマネージャーに報告する。

### 欠陥レポート

`テスト成果物/08_テスト実行/欠陥レポート.md` に書く(テストランをまたいで1つ)。表に1行足し、表の下にidの見出しを立てて詳しく書く。

```markdown
| ID | タイトル | 重要度 | 状態 | 見つけた日時 | 関連ID | 要求・仕様ID | テスト対象・環境 |
|---|---|---|---|---|---|---|---|
| BUG-001 | 17歳でも会員登録できてしまう | 高 | 未修正 | 2026-11-22 15:52 | LTC-002 | | v1.2 / Chrome 131 |
| BUG-002 | 設定画面のボタンが重なる | 低 | 未修正 | 2026-11-22 16:05 | SES-001 | スコープ外 | v1.2 / Chrome 131 |

## BUG-001

- 再現できる手順:
- 期待値:
- 実際の結果:
- 証跡: RUN-20261122-153000/証跡/LTC-002_1_shot.png
- 探索的テストで見つけた場合は、問題と判断した手がかり:
```

- **関連ID**: 実行していたローレベルテストケースのid、または見つけたセッションのid。
- **要求・仕様ID**: ふつうは空にする(見つけたテストから、影響する要求とリスクをたどる)。探索的テストでチャーターの外に見つけたときなど、見つけたテストと違う要求・仕様の不具合なら、その要求・仕様のidを書く。テストのスコープの外の不具合なら `スコープ外` と書く。どちらも、テストレポートの要求・リスクの不具合の数に使われる(`スコープ外` は数えないが、不具合の一覧には出る)。
- **重要度**: 要求や利用者への影響の大きさ。高 / 中 / 低。
- **状態**: 未修正 / 修正済み(確認テスト待ち) / クローズ(確認テストで直ったことを確かめた) / 却下(不具合ではなかった)。表には `未修正` `修正済み` `クローズ` `却下` のどれかを書く。
- 同じ不具合を2回書かない。すでにあれば、関連IDに足す。

## 確認テストとリグレッションテスト

テストマネージャーから指示されたときに行う。新しいテストランを作り、`実行情報.md` に修正された版(コミットなど)を書いて、指示されたテストケースと不具合だけを確かめる。

確認テストは、不具合の `関連ID` で確かめ方が変わる。

- **ローレベルテストケースがある不具合**: そのテストケースをもう一度実行し、ふだんと同じように結果を付ける。
- **セッションだけの不具合**(探索的テストで見つけたもの): もう一度実行できるテストケースが無い。欠陥レポートの「再現できる手順」のとおりに操作し、実際の結果を「期待値」と比べる。証跡は、不具合のidを入れた名前(`証跡/BUG-002_確認.png`)で残す。

どちらの場合も、欠陥レポートのその不具合の見出しに、確かめた結果を1行足す。前の回の行は消さない。次はセッションだけの不具合の例である(ローレベルテストケースがある不具合なら、実行したテストケースのidを書く)。

```markdown
- 確認テスト: RUN-20261123-101500 で再現できる手順を行い、期待値どおりになった。証跡: RUN-20261123-101500/証跡/BUG-002_確認.png
```

直ったことを確かめたら、表の `状態` を `クローズ` にする。直っていなければ `未修正` に戻し、足した行に何が直っていなかったかを書く。

リグレッションテストは、指示されたテストケースを、ふだんと同じように実行する。新しい不具合が見つかったら、新しい欠陥レポートを書く。

## 後からわかったこと

テスト実行の中で、前の工程で決めることがわかったら、テストマネージャーに報告する。どこまで戻すかはテストマネージャーが判断する。たとえば次のような場合である。

- 探索的テストで、仕様の疑問、足りないテスト条件、新しいリスクやテストのアイデアに気づいた(テストメモや課題に書いたものも含む)
- テスト環境の不具合でブロックになった
- E2E自動テストで、ケースごとの結果が取れなかった
- 手順が曖昧、画面が手順と違うなどで、テスト手順のとおりに操作できなかった
- 不具合が多く見つかった領域があり、リスクの発生確率を見直す必要がある

セッションシートに書いただけで終わらせず、報告に入れる。

## 終わる前に

- `python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" check --stage execution` を実行し、エラーを0件にする。警告(テスト結果が無いローレベルテストケース、セッションを行っていないテストチャーター)は、実行するか、未実行として理由を書く。前の工程の警告(テストケースで通していないカバレッジアイテムなど)が残っていることもある。それは前の工程で理由が書かれているかを見て、報告に書く。
- Fail のすべてに原因の分析があるか、テスト対象の不具合には欠陥レポートがあるかを確かめる。
- 共通ルールの「作成スキルが終わるときの報告」の4点に加えて、テストランのID、結果の件数、欠陥レポートのid、「後からわかったこと」を報告する。
