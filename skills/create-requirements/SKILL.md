# 要求仕様整理

あなたは要求仕様整理エージェントとして、テストベースを「要求」と「仕様」に整理する。ここで付けたidが、このあとのリスク・テスト条件・テストケース・テスト結果のすべての出発点になる。ここで抜けた要求は、最後までテストされない。

最初に共通ルール `${CLAUDE_PLUGIN_ROOT}/shared/conventions.md` を読む。

## 入力

- テストベース(仕様書、README、画面や利用者向けの説明など、テストを考えるもとになる資料)
- やり直しのとき: 回答が書かれた `質問表.md`、テストマネージャーから伝えられた変更の内容

テスト対象の実装は、資料に書かれていることの意味を確かめるためにだけ見る。実装をそのまま仕様として写さない。実装が間違っていたときに、間違いを仕様にしてしまうため。

## 進め方

### 1. 要求を整理する

テスト対象のシステムを、**誰が、何のために使うか**という利用者の視点で読み、利用者がそのシステムに求めることを要求として分ける。

- 1つの要求は、利用者にとっての1つの目的にする(「年齢を入力して会員登録できる」)。画面の部品や内部の処理の単位にしない。
- 性能・セキュリティ・使いやすさなど、機能以外に求められていることも要求にする。
- 資料に書かれていなくても、資料の内容から利用者が当然求めるとわかることは要求にしてよい。そのときは出典に「資料からの読み取り」と書く。

### 2. 仕様を整理する

資料に書かれている、確かめられる決まりを仕様として分ける。

- 1つの仕様は、合っているかどうかを1つずつ確かめられる大きさにする。「18〜65の整数だけ登録でき、範囲外はエラーを表示する」は2つに分ける。
- 数字・範囲・選択肢・状態・条件などは、資料に書かれているとおりに残す。後のテスト設計で境界値や組み合わせを出すもとになる。
- 出典(資料の名前と章・見出し)を書く。

### 3. 要求と仕様を紐づける

- すべての仕様に、もとになる要求のidを書く。
- **要求に紐づかない仕様**があったら、要求を見直す。その仕様が支えている利用者の目的があるはずなので、要求を足して紐づける。
- **仕様が無い要求**があったら、質問表に書く(種類は「抜け」)。仕様を推測で作らない。

### 4. 資料の問題を質問表に書く

整理の途中で気づいた曖昧さ・矛盾・抜けは、質問表に書く。工程は「要求仕様整理」にする。

## 出力

`テスト成果物/01_要求仕様/要求.md`

```markdown
# 要求

| ID | 要求 | 誰が | 何のために | 出典 | 備考 |
|---|---|---|---|---|---|
| REQ-001 | 年齢を入力して会員登録できる | 利用者 | サービスを使い始めるため | 仕様書 2章 | |
```

`テスト成果物/01_要求仕様/仕様.md`

```markdown
# 仕様

| ID | 仕様 | 要求ID | 出典 | 備考 |
|---|---|---|---|---|
| SPEC-001 | 年齢は18〜65の整数だけ登録できる | REQ-001 | 仕様書 2.1 | |
| SPEC-002 | 範囲外の年齢を入力すると、エラーメッセージを表示する | REQ-001 | 仕様書 2.1 | 文言は Q-001 で確認中 |
```

`テスト成果物/質問表.md`(無ければ作る。形は共通ルールを見る)

## やり直しのとき

- すでにあるidは変えない。変わった仕様は中身を直し、新しい要求・仕様には続きの番号を付ける。
- 無くなった仕様は行を消し、消したidをテストマネージャーに報告する(下流の成果物に影響するため)。
- 回答を反映した質問は、何をどう反映したかを報告する。質問表の `状態` を変えるのはテストマネージャー。

## 終わる前に

- `python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" check --stage requirements` を実行し、エラーを0件にする。「仕様が無い要求」の警告は、その要求が質問表のどの質問の `関連ID` にも書かれていないときに出る。出たら、質問表に書く。
- テストベースをもう一度通して読み、要求にも仕様にもなっていない記述が残っていないかを確かめる。
- 共通ルールの「作成スキルが終わるときの報告」の4点を報告する。
