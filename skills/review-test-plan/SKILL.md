# テスト計画レビュー

テストマネージャーとして、テスト計画の成果物をレビューする。テスト計画は、テスト全体の進め方と「どうなったら終わりと言えるか」を決める。終了条件が曖昧なままだと、最後のテストレポートで、やるべきことをやったかどうかを判断できない。

進め方は、共通ルール `${CLAUDE_PLUGIN_ROOT}/shared/conventions.md` の「8. レビューの進め方」に従う。確認のコマンドは `check --stage plan`。

## レビューするもの

- `テスト成果物/03_テスト計画/テスト計画.md`
- `テスト成果物/質問表.md`(工程が「テスト計画」の質問)

## 照らし合わせる入力

テスト計画スキルと同じ入力(`01_要求仕様/要求.md`、`仕様.md`、`質問表.md`、`02_リスク分析/リスク分析.md`)。

## 見ること

- **項目**: テスト目的、ドキュメント、テストアイテム、テストスコープ、対象外/制約、テスト終了条件、テストアプローチがそろっているか。
- **テスト終了条件**: 満たしたかどうかを、数字などで判断できる形になっているか。測り方が書かれているか。1つずつ「テストが終わったとき、これをどう判定するか」を自分で考えてみて、判定できないものは指摘にする。根拠の無い基準を、推測で決めていないか。
- **スコープ**: スコープと対象外が食い違っていないか。リスクが高いものを、理由と残るリスクを書かずに対象外にしていないか。
- **アプローチの抜け**: 高いリスクのすべてに、アプローチが紐づいているか。スコープに入れた仕様のすべてに、アプローチがあるか。
- **アプローチの選び方**: テストタイプが、仕様とリスクに合っているか(機能以外のリスクがあるのに、機能テストしか無い、など)。実施方法(E2E自動テスト / 手動テスト / 探索的テスト)の選び方に理由があるか。E2E以外の自動テストを計画していないか。
- **細かさ**: アプローチが、テスト全体の進め方の細かさにとどまっているか。詳しいテストケースを書いてしまっていないか。逆に「テストする」としか書いておらず、何をどんな考え方で確かめるかがわからないものはないか。
- **紐づけ**: アプローチに、根拠になる仕様と、対応するリスクが書かれているか。

## 直すときに気をつけること

- 終了条件の基準を決める根拠が無いときは、直さずに質問表に書く。
- リスクや仕様の抜けに気づいたら、ここで書き足さず、「後からわかったことの扱い」に乗せる。
