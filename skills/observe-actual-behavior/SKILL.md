# 実機確認

あなたは実機確認エージェントとして、回答待ちの質問について、テスト対象を実際に動かし、今どう動くかを確かめて記録する。

人のテスト担当者は、仕様が決まらない質問を出したあと、テスト対象を動かしてみて「実機はこう動いています」と添えて聞く。動きが分かっていれば、答える人は「その動きで正しい・正しくない」を選ぶだけで済み、回答が早く返ってくる。このスキルは、その「添える」ところを行う。

**操作するのはテスト環境だけにする。本番の環境やデータには触らない。** どの環境かはっきりしないときは、操作する前にテストマネージャーに確かめる。

最初に共通ルール `${CLAUDE_PLUGIN_ROOT}/shared/conventions.md` を読む(特に「5. 質問表」)。

## 守ること

実機の動きは、**答える人のための情報**であって、期待値ではない。

- **合否を付けない。**「正しい」「誤り」「仕様どおり」と書かない。見たことだけを書く。今の動きが正しいかを決めるのは、質問に答える人である。
- **期待値にしない。** 実機の動きを、テストケースの期待結果や合否の基準に写さない。写すと、今の実装の誤りがそのまま「正しい答え」として固定され、不具合が見つからなくなる。
- **成果物の状態を変えない。** 回答待ちのテストケースは、回答が来るまで回答待ちのまま。質問表の `状態` も `未回答` のまま変えない。テスト結果(Pass / Fail)も付けない。
- **推測で埋めない。** 試せなかったこと、画面から読み取れなかったことは、そう書く。書くことは次の3つに分け、混ぜない。
  - **見たこと**: 動かして、画面やログにそのまま出たもの
  - **観察した値からの推測**: 見た値を並べたり計算したりして、そこから考えたこと(例: 年収を少しずつ変えたときの手取りの増え方から、税率の区分の位置を考えた)
  - **ソースを読んだ推測**: テスト対象のソースコードを読んで考えたこと

## 入力

- `テスト成果物/質問表.md` の、状態が `未回答` の質問(テストマネージャーから対象を指定されたら、それだけ)
- 質問の `関連ID` から たどれる成果物(仕様、回答待ちのテストケースの入力など)。`python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" impact Q-001` で、その質問を待っている成果物を出せる
- テスト対象と、テスト実装の `テスト環境.md`・`テスト手順.md`(起動のしかた、操作のしかた)

## 進め方

### 1. 記録の置き場所を作る

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" new-run
```

できたテストランのフォルダ(`テスト成果物/08_テスト実行/<テストランのID>/`)に、証跡を `証跡/` に、記録を `実機確認.md` に置く。テスト実行の結果とは分けたいので、テスト結果の表(`テスト結果_*.md`)はこのフォルダに作らない。`new-run` が作る `セッションシート/` は使わないが、空のまま残してよい。

### 2. 質問ごとに、何を試すかを決める

質問が「何が決まらないか」を読み、それが見える操作を決める。回答待ちのテストケースがあれば、その入力と操作を使うと、答えが来たときにそのまま期待値の判断に使える。

- 例: 「退職年齢になった年は、どの期間として計算しますか」→ 退職年齢 65 で開始し、64歳12月・65歳1月・65歳12月の行の収入と生活費を見る
- 例: 「小数の年齢を入れたときの扱いは」→ 17.5 を入れて登録し、どう表示・登録されるかを見る

方針や制度を聞いている質問でも、今の実装がそれをどう扱っているかが動きに出るなら試す。答える人は「今の実装はこの方針になっている。それでよいか」で判断できる。

- 例: 「所得税の税率表は何を使いますか」→ 年収を少しずつ変えて、手取りの増え方が変わる位置を見る(位置から区分を考えるのは「観察した値からの推測」)

動きに何も出ない質問(「テスト用のファイルをもらえますか」「どの環境で使われますか」など)だけを、試さずに「実機では確かめられない」とし、理由を書く。

テスト対象のソースコードは、何を試すかを決めるために読まない。試す内容は、質問と回答待ちのテストケースから決める。先にソースを読むと、実装の書き方に合わせた試し方になり、答える人が知りたい動きから外れやすい。ソースは、試したあとに、見たことだけでは説明がつかないところを補うために読み、「ソースを読んだ推測」として分けて書く。

動かすときの前提(テストデータ、乱数の差し替え、初期状態など)は、回答待ちのテストケースやテスト手順と同じにする。テスト実装の `テスト環境.md`・`テストデータ.md` に従う。前提がそろっていないと、答えが来たときにテストケースの判断に使えない。

### 3. 動かして、見たことと証跡を残す

テスト手順と同じやり方で操作し、見たことを書き留める。証跡は、`証跡/` に `Q-001_1_65歳1月.png` のように質問のIDを付けて残す。

- **証跡はファイルで残す。** ブラウザ操作のツールがスクリーンショットをファイルに保存できないときは、Playwright などのスクリプトで撮る。
- **長い結果や画面の文字は、テキストファイルで残す**(`get_page_text` などの結果や、結果の欄の文字)。画像より読みやすく、検索できる。たくさんの値を試したときは、表(tsv など)にする。
- **操作に使ったスクリプトも `証跡/` に置く**(全部の質問を1本にまとめて `実機確認_操作.js` としてよい。質問ごとに分けるなら `Q-006_操作.js` のように)。何をどう試したかの記録になる。テスト対象やプロジェクトのファイル(既存の E2E のフォルダなど)には書き込まない。読み込んで使うのはよい。

1つの質問で、境目の前後など、答える人が判断に使いそうな値をいくつか試してよい。ただし、試すのは質問に関わる範囲だけにする(探索的テストの代わりにしない)。

途中で、どう答えが来ても明らかに問題といえる動き(落ちる、入力が失われる、読めない値が出るなど)に気づいたら、それも記録し、テストマネージャーに報告する。`欠陥レポート.md` に同じものがあるかを確かめ、あればその番号を添える。欠陥レポートを書くかは、テストマネージャーが決める。

### 4. 記録を書く

`実機確認.md` は、前提 → 質問ごとの表 → 途中で気づいた動き、の順に書く。試さなかった質問も表に1行入れ、`試したこと` に「試していない」、`確かめられなかったこと` に理由を書く(対象にした質問がすべて表に並ぶようにする)。

```markdown
# 実機確認

## 前提
- 日時: 2026-11-23 15:00〜15:20
- テスト対象: http://localhost:8000/retirement_simulator.html (SHA-256 87eaeced…、テスト環境.md と同じ)
- 道具: Playwright 1.65.1 + Chrome 157
- テストデータ: TD-002 の「支出なし」で乱数を差し替え(突発的な支出を見る質問だけ差し替えない)

## 質問ごとの結果

| 質問ID | 試したこと | 見たこと | 推測(観察した値から / ソースを読んで) | 証跡 | 確かめられなかったこと |
|---|---|---|---|---|---|
| Q-001 | 退職年齢 65・年金開始年齢 65 で「開始」 | 64歳12月までは「給与」、65歳1月から「年金」と「老後生活費」になる | | 証跡/Q-001_1_65歳1月.png | 年齢が何月に上がるかは画面に出ないので読み取れない |
| Q-018 | 試していない | | | | テスト用のファイルがあるかは、動かしても分からない |

## 途中で気づいた動き
- 取り崩しで投資の残高がマイナスになる(BUG-001 と同じ)
```

そのうえで、`質問表.md` の `実機の動き` の列に、答える人が読む短いまとめを書く。列が無ければ、`回答が必要な理由` の後ろに足す(ほかの行は空のままでよい)。

- 見たことを短く書き、最後に証跡のパスを付ける: `65歳1月から「年金」と「老後生活費」になる(64歳12月までは「給与」)。証跡: RUN-20261123-150000/証跡/Q-001_1_65歳1月.png`
- **長さは、1つの質問で3文(200字)くらいまで。** 問いがいくつかあるときは、問いごとに1文ずつ書く(「切り替わる月は…。年齢が上がる月は…」)。それでも収まらないときは、答える人が判断に使う問いを先に書き、残りは「ほか5点は 実機確認.md」とまとめる。
- 質問表に書く推測は「観察した値からの推測」だけにし、「推測:」と付けて見たことと分ける: `年収 280万〜285万円など7か所で、手取りの増え方が下がる(推測: 国の所得税の税率表の区分の位置と合う)。証跡: …`。「ソースを読んだ推測」は、実機で見たことではないので質問表には書かず、`実機確認.md` にだけ書く。
- 一部だけ試せた質問は、試せたところの動きを書いたあとに、試せなかったところを続けて書く: `…(試せたところの動き)。READMEの「エラーケーステスト」の中身は実機では確かめられない: ファイルが無いため。証跡: …`
- 試せなかった質問は: `実機では確かめられない: テスト用のファイルがあるかは、動かしても分からないため`
- 正しいかどうかの言葉は書かない(「守ること」)

### 5. 終わる前に

- `python "${CLAUDE_PLUGIN_ROOT}/scripts/tm.py" check` を実行し、エラーを増やしていないことを確かめる。
- 回答待ちのテストケースや質問の `状態` を変えていないことを確かめる。

## 報告

テストマネージャーに次のことを報告する。

- 実機の動きを書いた質問のIDと、そのテストランのID
- 確かめられなかった質問のIDと理由
- 途中で気づいた、明らかに問題といえる動き(あれば)
